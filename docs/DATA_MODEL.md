# Data model — stores, fields, and their invariants

> **On-demand reference.** Not loaded into every turn — read it when you touch this area.
> Decisions and their reasoning live in [`docs/adr/`](adr/); this file states current truth.

## Account institution registry (current)

`institutions` is a Tier-1, book-scoped table with `id`, `normalized_name`, and a payload
containing the mutable display `name`. `normalized_name` is unique within a book. An account
stores `institution_id` only; account reads hydrate the corresponding `institution` display
name. UI, REST and Lucius submit `institution` as a name, and the account service resolves or
creates the entity in the same transaction as the account write. `platform` was retired by
revision `202609121000_normalize_account_institutions` and is rejected on every write boundary.

Institution names can be renamed globally. Deletion atomically unlinks every affected account
and removes only the institution row; it never cascades to accounts or financial data. The
registry currently has no aliases, merge, connection configuration, or global provider catalogue.
Those intentionally deferred improvements are recorded in
[`docs/prd/2026-09-12-account-model-follow-ups.md`](prd/2026-09-12-account-model-follow-ups.md).

**accounts** (DB table since Plan 3 — see [Storage engine → the money core](#storage-engine) below for the schema; the field list and every invariant in this paragraph are unchanged from the `accounts.json` era) — `id, name, kind (asset|liability), type, platform, currency, opening_txn_id, archived`. CC fields: `statement_close_day`, `payment_due_day`, `reminder_days_before`. **Custodian model**: each broker/exchange has ONE securities account named after the custodian (e.g. `"IBKR"`) holding all positions, lots, and grants regardless of quote currency, plus separate currency cash wallets (e.g. `"IBKR USD"`, `"IBKR SGD"`). The `platform` field is the custodian grouping key — set identically on the securities account and all its currency wallets. Positions/lots/grants always belong to the securities account; cash legs of trades (buys, sells, dividends) hit the matching currency wallet. **An account's opening balance is ONE fact: `opening_txn_id`** (RFC `.claude/rfcs/2026-07-31-opening-balance-is-one-fact.md`, completing ADR `2026-07-28-starting-balance-single-surface`). It points at that account's single `kind="adjustment"`, `cleared=True`, `category=None`, `description="Starting Balance"` transaction. The **opening amount** is that row's signed leg (positive→to-leg, negative→from-leg; `0.0` is a legal opening booked as a zero to-leg — "my balance was zero when tracking started"), and the **tracking-start cutoff** is that row's `date`. Neither is stored on the account: `initial_balance` and `initial_balance_date` were DELETED from storage, along with the row's `source: "opening"` column and its `external_refs: [{"source": "opening", "ref": <account_id>}]` entry (the row now stores `source: "manual"` and no refs — the opening is a number the user asserted by hand). `opening_txn_id: null` = no tracking start at all; every leg counts. **One marker, one read path** — there is no fallback, no dual read, no absent-field tolerance anywhere. `ledger.set_account_opening(account_id, amount, as_of)` is the ONE writer (mints or patches the row IN PLACE, keeping its id, then points the account at it); the read side is `ledger.opening_amount(account)` / `opening_date(account)` / `cutoffs_by_account(accts, txns)` (the loop-hoisted map) / `opening_txn_ids()` (the O(1) "is this row an opening?" set) / `opening_index(txns, accts)`. The balance fold takes the cutoff as an ARGUMENT — `account_balance(account, txns, opening_date)`, likewise `cleared_account_balance` and `account_balance_as_of` — and `is_before_tracking_start(leg_date, opening_date)` is a pure date comparison, so a fold site that forgets the cutoff is a TypeError, not a silent miscount. There is no separate opening seed in the fold: the row is itself a leg, dated exactly at the cutoff, and the strict `<` always counts it. **The drift is unrepresentable** — the cutoff is READ OFF the row, so it cannot lag behind a re-dated opening (the old two-field shape did, and the strict `<` then made the opening exclude ITSELF and collapse the balance to 0). A DANGLING pointer RAISES `DataIntegrityError` on every READ, naming the account and the id — it never degrades to None, which would silently un-curtain the account's pre-start history and move its balance. The WRITE choke is the deliberate exception: `set_account_opening` treats a missing target as "no row" and re-mints (`_opening_row_to_patch`), and `opening_for_edit(account)` is that same tolerant resolve for an edit that supplies only one of amount/date — so the state is repairable without hand-editing `accounts.json`. Creating it is prevented upstream: in the JSON era, `accounts.json` and `transactions.json` were ONE checkpoint unit (`ai.checkpoint._COMPANIONS` — a turn writing either captured both, so a restore reverted the pair atomically; ADR `2026-08-01-referential-file-pairs-revert-together`). **Since Plan 3's DB cutover this pairing is structurally obsolete and `_COMPANIONS` is permanently empty** — row-level `write_log` images (spec D7) capture every touched row in every table a turn touches, with no table-name pairing map needed: a `set_account_opening` write composes `accounts`+`transactions` through one `locked_unit_of_work`, so both rows land in the same checkpoint and restore reverts them together by construction. ADR `2026-08-08-money-core-tables-verbatim-payload-plus-promoted-columns`. `GET/POST/PUT /api/accounts` and the AI `create_account`/`update_accounts`/`list_accounts` keep `initial_balance`/`initial_balance_date` as **input parameters** and as **derived response fields** (`account_with_balance`) — the wire contract did NOT move, only the storage. `opening_txn_id` is SERVER-OWNED: absent from `AccountCreate`/`AccountUpdate` and from `_ACCOUNT_UPDATE_FIELDS`, and explicitly refused by `services.accounts.assert_no_server_owned_fields` (a caller-settable pointer would hand one account another account's balance). Every account create requires `initial_balance` (zero is valid and still mints today’s row), and `services.accounts.create_account` commits the account, row, pointer, and audit in one DB transaction — never two store writes from a router. The row is structurally protected: `update_transaction` takes a NARROW path on it (`_apply_opening_txn_edit` — amount and date only, rerouted through `set_account_opening` so it keeps its id; a patch key that would change anything else is refused), `bulk_delete_transactions` refuses it outright (`ConflictError`/409), `set_transaction_cleared` refuses to uncleared it, and the filter-based `DELETE /api/transactions` sweep skips it via a `protected_ids` parameter the service choke `ledger.delete_transactions_where` supplies (a store must not read another store — pinned by an AST test asserting `bulk_delete_where` has exactly ONE caller). `tracking_start.align_tracking_start`'s Preserve rewind is now ONE write: it re-dates AND re-amounts that row. One-shot migration: `backend/scripts/migrate_opening_txn_pointer.py` (dry-run default, `--apply`, data-dir backup; computes every account's balance with the OLD fold before and the NEW fold after on an in-memory simulation and REFUSES to write if any moves, then re-verifies after writing; idempotent and re-runnable — run it again after an `ai/checkpoint.restore()` of a pre-migration `accounts.json`, which writes raw bytes past every store). It writes in **two independently idempotent phases** — (A) mint/adopt rows + write pointers while KEEPING `initial_balance_date`, (B) strip the legacy keys and row markers — so a kill -9 anywhere leaves a book the next run resumes rather than one that reads as "already migrated"; it refuses on a dangling pointer, on a lost cutoff, while another process is writing the book (file-digest guard + a `:8080` probe), and — since a re-dated opening moves the account's HISTORY while today's balance is unchanged — until `--accept-history-shift` signs off on the per-account deltas it prints. ADR `2026-08-01-migrations-write-the-new-fact-before-deleting-the-old`. ADR: `docs/adr/2026-07-31-opening-balance-is-one-fact.md`. **`external_ids: [{source, ref, name, mask, linked_at}]`** (RFC connectors-as-data-sources §D, replacing the nine provider config stores' own `account_map` blobs) links a provider account to this one — a `(source, ref)` pair may be held by at most ONE account (`services.accounts.assert_external_ids_unique`, called from `create_account` and the `update_account` choke; a collision raises `ValidationError` naming the holder). Linking fills `last_four`/`platform` from the entry's `mask`/`institution` ONLY when they're currently blank (`institution` is read at link time and never itself stored on the entry). `connected` is DERIVED (`bool(external_ids)`), stamped fresh on every `account_with_balance` read — never independently trusted, and absent from `AccountCreate`/`AccountUpdate`/the `create_account`/`update_accounts` AI tools' writable fields (the stored `connected` column is legacy dead weight a pre-RFC row may still carry; nothing reads it). Each `external_ids` entry is also hydrated with `provider_label` on read (`services.accounts.provider_label`, sourced from `services.aggregation.providers.PROVIDERS[source].label`, falling back to the raw source string) — server-side, so no frontend copy of the provider-name table is needed. Backfilled once by revision `202609051210_account_external_ids_from_config_maps` (moves every provider's `account_map` entry onto its account, then strips `account_map`/`poll_interval_seconds`/`cursor`/`server_knowledge` off the nine provider `secret_config` rows — the scheduled sync pipeline that read them is gone). `GET /api/connectors/{id}/accounts` returns the per-provider account list via `services.connector_fetch.provider_accounts` (RFC connectors-as-data-sources §A/§E — live `currency`/`balance` plus each account's own `linked_account_id`/`provider_label`), falling back to the LINKED-only block (derived from `external_ids`; `currency`/`balance` are `None`) only when that service import fails (e.g. an id that isn't one of the nine aggregation providers) — see `api/connectors_api.get_connector_accounts`'s own docstring for the seam.

**Account types — one axis** (ADR `2026-09-07-seven-account-types-one-axis`, spec `docs/superpowers/specs/2026-09-07-account-taxonomy-design.md`). `type` is the ONLY classification a caller sets; `kind` (`asset`|`liability`) stays a column but is DERIVED from `type` and rewritten server-side on every write — never accepted on `AccountCreate`/`AccountUpdate` or the AI `create_account`/`update_accounts` tools. Seven values, each fixing kind/spendability/budget membership/band in one row (`backend/models/account.py`: `LIABILITY_TYPES`/`ON_BUDGET_TYPES`/`SPENDABLE_TYPES`/`ACCOUNT_BAND` are the lookup tables every consumer reads instead of special-casing a type name; `kind_of`/`band_of`/`is_liability` are the derivation functions):

| Type | Kind | Spendable | On budget | Band |
|---|---|---|---|---|
| `cash` | asset | yes | on | `cash` |
| `fixed_deposit` | asset | no | off | `fixed_deposit` |
| `investment` | asset | no (runway toggle) | off | positions by instrument class + `settlement_cash` (signed — negative = drawn margin) |
| `retirement` | asset | never | off | `retirement` |
| `receivable` | asset | no | off | `receivable` |
| `credit` | liability | — | on (payment envelope) | `credit` |
| `loan` | liability | — | off | `loan` |

Any other `type` value RAISES at the store — there is no fallback default. **Fields kept, shown by type**: `apr` (credit, loan — the "interest rate", no new field), `credit_limit` + `statement_close_day`/`payment_due_day`/`payment_due_date` (credit), `principal`/`payoff_date`/`min_payment` (loan), `apy` (cash, fixed_deposit); `platform`, `last_four`, `color`, `note`, `connected`, `archived` apply to every type. `reminder_days_before` remains readable only as legacy persisted metadata; account saves do not expose or act on it because reminders belong to Automations. **Removed from `Account`/`AccountCreate`/`AccountUpdate` and every client-facing schema**: `asset_class` (free-form band-key string), `locked`, `on_budget` (override), `group` (sidebar override).

**Net-worth bands**: `cash`, `fixed_deposit`, investment positions by instrument class (`equity`/`crypto`/`commodity`/`bond`/`option`), `settlement_cash` (may be negative), `retirement`, `receivable`, `credit`, `loan`, plus owned-asset bands (`property`/`commodity`/`other_asset`). Retired: `brokerage_cash`, the account-side `property` band, `bank_cash_base`/`brokerage_cash_base`/`liquid_net_worth_base`.

**Migration** `202609071200_seven_account_types` (Alembic, fail-closed — an unmapped legacy type RAISES) collapses the old 26 types onto the seven (`checking`/`savings`/`cash`/`ewallet`/`debit_card`/`money_market`/every aggregation connector's default → `cash`, a `locked` payload → `fixed_deposit`; `brokerage`/`crypto_exchange`/`custody` → `investment`; `pension`/`retirement_acct`/`govt_fund` → `retirement`; `loan_receivable` → `receivable`; `credit_card`/`line_of_credit`/`bnpl` → `credit`; `mortgage`/`personal_loan`/`auto_loan`/`student_loan`/`margin`/`other_debt` → `loan`) and CONVERTS every property-like account (`real_estate`/`vehicle`/`collectible`/`other_asset`, or any account whose payload set `asset_class`) into an owned asset — newest mark = the account's balance on migration day, `cost`/`cost_date` from its Starting Balance row when present, `loan_account_id` left unset for the user to link on the Assets tab, the account archived with its transactions retained. `net_worth()` is invariant across the migration, to the cent.

**transactions** (DB table since Plan 3, with `transaction_splits`/`transaction_external_refs` as child tables — see [Storage engine → the money core](#storage-engine) below for the schema; every field/invariant below is unchanged from the `transactions.json` era) — two-leg: `id, date, kind (expense|income|transfer|adjustment|investment), description, memo, category, payee_id, from_account_id/amount/currency, to_account_id/amount/currency, original_amount/currency, base_amount, base_currency, fx_rate, tags[], splits, cleared, external_refs[], deleted`. **Provenance/dedup is ONE ordered list (ADR `2026-07-21-collapse-external-refs-to-one-list`, superseding the 2026-07-20 scalar+list layout — the combined `external_id` string stays FULLY RETIRED): `external_refs: [{source, ref}]`, always present (may be `[]`). Entry `[0]` is the creation-time origin (`source` namespace: `email`/`opening`/`recurring`/`ibkr`/`vest`/`option-premium`/`ofx`/`csv`/`simplefin`/…; `ref` the raw per-event id: Message-ID hash/FITID/`acct:txn`/content-hash); later entries are pairs absorbed by the merge/dedup-review flow. EVERY pair is an L0 idempotency key — `TransactionStore.by_external_ref(source, ref)` matches anywhere in the list. `core.txn_sources.ext_ref_pairs(row)` (leaf, shared by `db` + `matching`) reads the list as a set; `primary_pair`/`primary_source`/`primary_ref` are the one definition of "the" origin for display/actor-inference readers; `is_authoritative_source(source)` is unchanged. The model-facing `add_transactions` tool exposes `external_refs` (item `{source: enum["email"], ref}`; "copy the message_id verbatim") and REFUSES the retired flat `external_source`/`external_ref` spelling loudly. No writer ever constructs a combined string. **The email id the model books is a SHORT SERVER-COMPUTED HASH** — `core.email_ids.internal_email_id(raw)` (`sha256(canon(raw))[:12]`); `imap_client` extracts the raw Message-ID (or `content_fallback_id` when absent — a folder-independent content hash, replacing the folder-unstable `uid-<validity>-<uid>`), `_render_emails` shows the model ONLY the short id, and `email_snapshots` (the DB table) keys on the same id — so the model is entirely OFF the identity path and cannot garble it. One-shot migration: `backend/scripts/migrate_external_id_split.py` (dry-run default, `--apply`, backup, idempotent — splits `external_id` on the first colon and deletes the old key).** **The freeform text is split on PROVENANCE (ADR `2026-07-17-split-note-into-description-and-memo`, supersedes the 2026-06-29 merge-into-`note`): `description` = the bank-origin / matching string — the ONLY freeform field read by dedup (`matching.py`), spend rules, payee resolution, and the import `external_ref` hash; `memo` = the user's personal annotation (order items, who you were with) — display-only, read by NONE of them, so editing it never perturbs matching.** The pre-split `note` is GONE from storage AND from every WRITE-facing surface (ADR `2026-07-20-retire-transaction-note-input-alias`, one-shot, no input-side shim left anywhere — the owner's directive was explicit: "just use description only, stop having backward compatible code for old ones"). Every duplicated `note`→`description` acceptance was removed in the same change: both scheduling AI-tool schemas (`schedule_task`/`update_scheduled_task`'s recurring-transaction template, which now declares `description`+`memo` instead), `ai/tools/_shared.py`, `mcp/adapter.py`'s write-audit summary, `models/transaction.py`'s scaffold, `api/ledger.py`'s REST request models (`TransactionCreate`/`TransactionUpdate`/`BulkTxnChanges`/`BulkTxnUpdateFlat`), `services/ledger.py`'s three choke points (`create_transaction`/`bulk_create_transactions`/`update_transaction`), `services/ledger_preview.py::preview_update`, and `db/transaction_store.py::make_transaction` — a caller still sending `note` now has it silently ignored, not aliased. A live bug surfaced by the sweep: `services/options.py`'s premium/close cash-leg booking was itself passing `"note"` instead of `"description"` into `create_transaction`, relying entirely on the now-removed alias — fixed to pass `description` directly. What SURVIVES, deliberately, is READ-ONLY: `TransactionStore._load_items` still lazily backfills `description` from a still-present `note` on read (an un-migrated on-disk book — this is a self-hosted app and the migration script is opt-in, not a boot migration — must never have its descriptions silently blanked), and `db.transaction_store.txn_text(t)` (`description or note`, never `memo`) is still the shared read helper for matching/rules/payees, covering a raw dict that bypasses the store; `services/rules.py`'s own copy of this fallback was collapsed to delegate to `txn_text` rather than re-implementing it. `services/scheduling.py`'s recurring-transaction runner keeps the identical read-only `note` fallback for the same reason, scoped to `scheduled_tasks.json` (checked live: zero affected tasks on the one accessible install, so no migration script was needed there — see the ADR). One-shot migration: `backend/scripts/migrate_note_into_description.py` (dry-run default, `--apply`, backup, idempotent — NOT a boot migration). The per-line split `note` (`splits[i].note`) is a DIFFERENT field, unchanged, as is the register search bar's unrelated `q_field="note"` scope value (spans description+memo by design, never part of the AI tool schema). `base_amount`/`base_currency`/`fx_rate` are stamped at write time (the transaction-date rate); `txn_base_amount()` TRUSTS `base_amount` while `base_currency` matches the current base (the historical-rate lock, ADR 2026-07-09) and only recomputes on a base-currency change or a legacy/unstamped row — a completed foreign txn's base value is a historical fact, not revalued as the market drifts (transfers now also stamp these at write time; held foreign BALANCES still float at the current rate in net worth). `original_amount`/`original_currency` capture the pre-conversion foreign charge (e.g. an SGD card billed in USD) — DISPLAY/AUDIT only, never read by `txn_base_amount`/balances/splits; explicit input wins, else auto-captured from the converted primary leg at the create choke point (transfers skipped). `kind=investment` is a cash leg tied to a position (single cash leg, from XOR to) and carries an OPTIONAL user-chosen category — net-worth folds are kind-agnostic, so investment is value-neutral on its own. `category` is for expense/income/investment/transfer (never a kind name; `adjustment` rows carry None, always); income with no specific label stays `None` (Uncategorized) and still counts as Ready-to-Assign inflow. A `kind=transfer` row may ALSO carry an optional category (owner decision 2026-07-03) — the Plan tab's activity fold, not the write path, decides whether it drains/credits an envelope (see the Planning section's "categorized transfer" rule and `docs/adr/2026-07-03-categorized-transfers.md`).

**Split transactions:** `splits: [{category, amount, note}]`; top-level `category="split"` sentinel. Expense/income only; Σ amounts == leg ±0.01. `txn_split_base_amount = split.amount / leg × txn_base_amount`.

**Positions:** the `instruments` table (what) + the `positions` table (how much) + the `price_points` table (prices). Read via `positions_service.hydrated()`. `apply_position_change(add)` REFUSES a second active liquid position for the same instrument×account (returns the existing position_id — a buy of an existing holding is a lot acquire, not an add); with `acquired_at` the add auto-records the buy lot and returns its `lot_id`, and the caller's `idempotency_key` lands on that auto-lot (automated flows MUST pass the broker order id so a redundant `acquire_lots` / retry dedupes to a no-op). **Multi-position read surfaces (custodian model)** — "one liquid position per instrument×account" is a PER-ACCOUNT invariant, not portfolio-wide: the same instrument held at two custodians is two position rows. `services/asset_detail.py::_position_block` aggregates across ALL of an instrument's liquid positions (summed qty/value, each position's cost converted to base individually — never mixed raw; unrealized P&L is null the instant ANY contributing position's cost is unknown) and exposes a `per_account` breakdown + a `position_id` that's non-null only when exactly one position contributes; it also folds in `vesting_state="unvested"` exposure as a separate `unvested` block ({units, market_value_base, grant_id, next_vest}) so an equity-grant holding shows both vested and unvested units instead of hiding the latter. The Holdings tab (`useInvestmentsBook.mergeByInstrument`) mirrors this: rows of the same instrument merge into one (summed base value/P&L, recomputed weight, today% unchanged since it's per-instrument) whenever the active "Group by" does NOT itself distinguish accounts (asset class/currency/none) — grouping by account is exempt. No venue sublabel anywhere (owner decision) — a merged row's account field is a bare count ("2 accounts"). Crypto's asset-detail headline + chart always render in the portfolio BASE currency (`asset_detail._display_currency`, no caller override) — never a per-holding cost-currency preference.

**Instrument identity** (ADR `2026-07-15-instrument-identity-canonicalization-front-door.md`) stays feed-keyed — `(price_source, price_source_id)` is still the identity key, unchanged — but `resolve_instrument` (the SINGLE implementation, `services/instruments.py`; `api/instruments.py`'s REST route and the AI tool both delegate to it) now runs a dedupe/canonicalization FRONT DOOR before minting a new instrument: (1) a Yahoo-style crypto pair (`"BTC-USD"`, `"eth-eur"` — a recognized ISO-4217 fiat suffix, base confirmed by a real CoinGecko hit) canonicalizes to the underlying coin via CoinGecko instead of minting a separate yahoo-priced instrument per fiat pairing; metal codes are excluded from pair-detection. (2) The `identifiers` bag (`isin`/`figi`/`mic`/`coingecko_id`) is populated at resolve time with whatever's free (yfinance's `Ticker.isin`, best-effort) and becomes load-bearing for dedup. (3) `find_existing(candidate, store, allow_duplicate_symbol=False)` tries, in order: exact `(price_source, price_source_id)` → a shared `identifiers` value → normalized symbol + same `asset_class` (silently reused for **crypto** — a symbol collision there is essentially always the same coin; **REFUSED** — `ValidationError`, existing id/symbol/name in `context` — for everything else unless the caller passes `allow_duplicate_symbol=true`, since a stock ticker genuinely can be two different companies on two exchanges). A manual instrument with no `price_source_id` (which never hits the exact-key dedupe) routes through the same symbol+class ladder step. The explicit `price_source`+`price_source_id` fast path is UNCHANGED — no ladder, no refusal (a caller-supplied external id is authoritative). REST (`POST /api/instruments/resolve`, `POST /api/intel/assets/resolve`) surfaces the refusal as 422; the AI tool exposes `allow_duplicate_symbol` as a schema param. Broker-sync paths (`aggregation/alpaca.py`, `aggregation/ibkr.py`, `benchmark_seed.py`) call `InstrumentStore.find_or_create` directly with an explicit id and are unaffected (exact-key only, deliberately — an unattended sync job can't confirm a collision).

**Tax lots:** the `lots` table (`LotStore`). FIFO = (acquired_at, created_at). Kinds: `buy | drp (dividend reinvestment) | transfer_in | grant | opening` (a DRP lot keeps its provenance; FIFO/term/double-book treat it exactly like buy). Unknown basis → `realized_gain=None` (never 0). $0 taxable proceeds REFUSED. A non-taxable disposal may carry `transfer_to_account_id` (resolved id of ANOTHER of the user's accounts; id or exact name accepted at the choke) — a LABEL saying where the shares went, not a second leg: the receiving `transfer_in` lots are still acquired separately, and the field is refused on a taxable sale, a non-zero price or beside `proceeds_account_id` (ADR `2026-09-05-transfer-destination-is-a-label-not-a-leg`). **Historical-rate lock for lots (ADR `2026-07-15-lot-historical-rate-lock`, mirrors the ledger's):** acquire stamps `fx_rate` (exact cost→base multiplier at write time) + `base_currency` on the lot; a disposal whose consumed lots ALL carry trusted stamps books a per-leg `realized_gain_base` (proceeds at the disposal-date rate − Σ basis at each lot's acquire rate — the tax-standard decomposition that captures the basis FX gain); `realized_pnl` TRUSTS the stored `realized_gain_base` while the event's `base_currency` matches the current base, recomputing from the native gain only on a base change or unstamped legacy/`opening` rows. **A position's `quantity`/`cost_basis`/`cost_currency` are DERIVED from its records** (ADR `2026-10-07-a-position-quantity-is-derived-from-its-records`): `position_figures.rederive` is the only writer. Owned positions = Σ open lots (mixed-currency lots FX-convert into the instrument's quote currency, never a raw cross-currency average). A grant's locked position = unvested tranche units. A grant's pending position = parked vest units. Neither grant position holds lots (revision `202610111300_grant_holdings_hold_no_lots` removed the ones the old read seeded). `update_position` refuses direct writes to them on EVERY position, and an `account_id` move re-files the position's lots with it. An add with no `acquired_at` books an `opening` lot dated today; nothing seeds a lot on read (`ensure_opening_lot` is gone — revision `202610111200_every_holding_has_a_record` gave legacy lot-less holdings theirs). Choke: `lots_service.apply_lot_change(change)` — acquire and dispose are both idempotent on a client `idempotency_key` (automated flows pass one so a reprocessed email/retry can't double-book). A `kind=buy`/`drp` acquire identical to a fully-open lot on the same position (same `acquired_at`, qty, `unit_cost`) is REFUSED as a double-book (returns `existing_lot_id`) unless `allow_duplicate=true`; grant/vest lots and partially consumed matches are exempt. Symmetrically, a disposal matching an already-recorded sale on the same position (same `disposed_at`, qty, `proceeds_per_unit`, currency — `method` and `disposal_fees` EXCLUDED so a re-entry under a different lot method is still caught) is REFUSED as a double-book (returns `existing_event_id`) unless `allow_duplicate=true`. A disposal is reversible via `type="dispose_undo"` (event_id): re-opens the lots it consumed (capped at original_qty), soft-deletes its cash-proceeds leg if any, deletes the realized event, resyncs — REFUSED if a consumed lot no longer exists (shares can't be cleanly restored).

**Position axes (ADR `2026-07-31-split-position-bucket`):** the old overloaded `bucket` is
gone, replaced by TWO orthogonal fields. **`vesting_state`** (`vested` | `unvested`) is
STORED on the position and is the ONLY thing net worth filters on — `unvested` is written
solely by the equity choke and means "forfeited if the grantee leaves", so it is excluded
from net worth and reported as `unvested_base`. **`liquidity`** (`liquid` | `semi_liquid` |
`illiquid`) is DERIVED per read by `positions_service.liquidity_of` and says nothing about
entitlement — property is `illiquid` AND `vested`; a grant's pending-release position is
`semi_liquid` AND `vested`. Conflating the two is what nearly deleted real property from net
worth. `position_store.vesting_state_of` maps legacy rows on read (`locked`→unvested,
`liquid`/**`contingent`**→vested — contingent meant fully-entitled, NOT the accounting
sense); `backend/scripts/migrate_position_bucket_to_vesting_state.py` retires the key on disk.

**Equity comp:** the `grants` table (`GrantStore`: type rsu|ltip, instrument_id, grant_date, flat tranche list with stable ids, `tax_event at_vest|deferred`, `locked_position_id`, optional `grant_price_per_unit` — reference only, never basis/tax; `grant_create` is idempotent on a client `idempotency_key` like every other money-fact store) + the `vest_events` table (`VestEventStore`, append-only, idempotency-keyed, links txn_id/lot_id for undo). Choke: `equity_service.apply_equity_change(change)` — vest_apply is one transaction in fixed order (FMV-basis lot on the liquid sibling → vest_event append + tranche marked vested → the locked and pending positions RE-DERIVED from those records, never ± arithmetic). **A vest writes NO ledger transaction, whatever the `tax_event`** (ADR `2026-09-22-a-vest-books-no-income-transaction`): it is compensation paid in SHARES, so the custodian account receives no money — booking an income leg into it while ALSO minting the lot moved net worth by twice the vest (`Σ account balances + Σ market values` counts both), overstating a real book by ~S$26k on one vest. Tax at vest is information, not a money movement: units/FMV/currency/dates/`gross_gain_native` all live on the vest event, which is what `equity_report` reads. **Two-step vest** (ADR `2026-07-31-two-step-vest-pending-release`): a grant with `release_required=true` models plans that DELIVER shares after they vest (settlement lag, blackout, country delivery rules) — `vest_apply` then parks the units in a `bucket="contingent"` **pending-release position** (`grant.pending_position_id`, quantity-only, NO lot — the same shape as the locked position) and the separate `release_apply` op moves them onto the liquid FMV lot. A release moves SHARES ONLY (never writes/edits/deletes a txn) and the lot it creates is back-stamped to the VEST date and vest-date price, so a delivery lag cannot move money, change basis, or restart a holding period; it is all-or-nothing, and the flag affects FUTURE vests only. `vest_undo` has two shapes accordingly (pending → drain the pending position; delivered → delete the lot). Both the locked AND pending positions are grant-managed (hand-edits to quantity/bucket refused). Default `release_required=false` keeps the one-step path unchanged. Unvested units = a real `bucket="locked"` position whose quantity is DERIVED from the grant's not-yet-vested tranches (0 once the grant is cancelled) by `position_figures.rederive`. Vest taxability is re-derivable per jurisdiction from the `vest_events` table's facts whenever a tax engine is built — the write path has never stamped a verdict (ADR `2026-07-12-options-tax-facts-not-verdicts`), and as of 2026-09-22 it writes no transaction to stamp one ON. `vest_event.txn_id`/`lot.txn_id` are `None` for vests recorded after that change; events written BEFORE it keep a real id, and both `vest_undo` (soft-deletes it) and `equity_report` (recomputes base from it) still honour one when present. (The tax engine itself was REMOVED 2026-08-25, ADR `2026-08-25-remove-the-tax-feature`; `services/equity_report.py` survives as a pure per-year VEST report — it reads vest_events and recomputes gross gain, never trusting snapshots.) Daily `vest_reminder` task action (deterministic, no LLM) seeded on first grant. **Unvested
value is EXCLUDED from net worth** — `ledger.net_worth()`/`net_worth_history()` and
`portfolio_history`'s lot reconstruction all skip `bucket="locked"` positions/lots, reporting
their value separately as `unvested_base` instead (forfeited if the grantee leaves, so not
owned yet; ADR `2026-07-31-unvested-equity-excluded-from-net-worth`). RFC: `.claude/rfcs/equity-comp.md`.
`GET /api/net-worth` (`ledger.net_worth()`) is the ONLY net-worth computation — the frontend
consumes it (`hooks/serverState/useNetWorth.ts`) rather than re-summing `usePortfolio()` rows,
after that client-side duplicate drifted from it (unvested equity double-counted; ADR
`2026-07-31-single-source-net-worth`). `usePortfolio()`'s own `portfolioTotal` is a
PORTFOLIO/allocation total (rows sum, live-priced) — the denominator for allocation %/venue
breakdowns, never net worth.

**Statement match policy** (RFC `.claude/rfcs/2026-07-29-one-match-engine-instructions-as-policy.md` §D5/§D6, Phase 3) — the owner's free-form statement notes ("no drift in date") become a `services/matching.MatchPolicy` the engine performs as arithmetic, instead of prose `lucius_pass` re-judges per row per import. **Four layers, broadest first, most specific wins field by field** (`services/statements/match_policy.resolve_policy`): (1) `MatchPolicy()` — the engine's own constants; (2) **global** statement skills' `metadata.match_policy` (a JSON **string** — `SkillStore.metadata` values are strings — read by `skills_service.match_policy_layers`); (3) **account-scoped** statement skills' same field; (4) this source's remembered/typed instructions via `match_policy.derive_policy` (ONE bounded `core.llm_seam.complete_json` call, cost/task-model source key `statement_match_policy`, notes ridden FENCED via `core.untrusted`). Every layer — the model's reply AND the skill metadata alike — passes the `_EXTRACTABLE_FIELDS` allowlist + clamping in `extract_fields`: unknown keys dropped structurally, `max_date_drift_days` clamped into `0..FETCH_WINDOW_DAYS`, `amount_tolerance_pct` into `0..TWIN_SETTLED_DRIFT_TOL`, and only the TIGHTENING side of each boolean accepted (`currency_strict=True` / `drift_matching=False`) so no narrow layer can un-tighten a broad one. A failed/empty extraction yields `MatchPolicy()`. **`weak_tier` is not a `MatchPolicy` field and does not appear in the model-facing schema** — it is a call-site keyword only `decisions._apply_batch_match` passes; the engine's one loosening switch must be unreachable from any data path. **`blocked_account_ids` is never accepted from the model**: it emits account NAMES it read in the notes (the extraction prompt carries NO account list at all), resolved server-side against ONLY the statement's routed accounts; an unresolvable name is dropped, never blocked-by-default. **Cache keys — TWO levels, covering different things** (R6's "cached forever" was wrong: `remember_instructions` stores nothing for a csv/xlsx with no profile, and `_document_fingerprint` returns `None` for a short PDF; an image-only scan keys by its masthead image instead — `services/statements/page_hash.py`, nearest `img:` key within `MAX_DISTANCE` bits, ADR `2026-09-05-a-scanned-statement-is-identified-by-its-masthead-image`). (a) **Cross-FILE**, on the **format profile**: the *extraction* (`{"fields": {...}, "note": str}`, account names still names) in `StatementFormatStore.match_policy` + `match_policy_instructions_hash`, written together in one `set_match_policy` save so a failed write leaves both unset and the next preview re-derives. (b) **Same-FILE**, on the statement record: `match_policy_source` (layer 4's fields) + `match_policy_note` + `match_policy_instructions_hash`, which is what makes a re-preview free for a source that has no fingerprint at all. A miss on both is additionally bounded by `_MAX_POLICY_ATTEMPTS = 3` (`match_policy_attempts` on the record — the `hints_attempts` precedent), so a source whose extraction keeps returning malformed JSON stops re-billing; a SUCCESS is stamped and never retried, so the cap only bites on repeated failure, and running out is safe because the preview stamps the policy it actually matched under. The record also stamps `match_policy` (resolved, all layers merged) and **`match_policy_hash` = sha256 of the RESOLVED policy + the sorted routed-account set — NOT `parse_instructions_hash`**, which covers only one layer of four (editing a skill's policy between preview and commit would otherwise move the acceptance set invisibly). `decision_commit` re-resolves the deterministic layers and REFUSES on a mismatch, and refuses an absent stamp when `parse_instructions_hash` is present — there is deliberately no `except → MatchPolicy()`, because absence yields the LOOSER policy. **⚠️ "Monotone-tightening ⇒ safe" is FALSE**: tightening MANUFACTURES duplicates (`default_action` is `"create"`, so suppressing every match books a re-import as N new rows behind a clean-looking preview) and REDIRECTS merges onto different real ledger rows. So `_flag_policy_suppressions` diffs the policy against `MatchPolicy()` and the preview reports `match_policy.suppressed` (index, `suppressed_id`, `existing`, `replaced_by`) with a per-row `policy_suppressed` flag; those rows carry `draft["policy_suppressed"]` and **default to SKIP, not create**. §D7 consequence: `lucius_pass`'s `reject_match` prompt keeps exactly ONE reason (the match's own note names a different merchant) — the day-gap / currency / no-drift reasons are now enforced mechanically before a proposal exists. The **post-commit** ledger-diff panel (`ledger_diff.uncovered_ledger_rows`) reads that same stamp through the shared `decisions.rederive_match_pass`, and WITHHOLDS itself (`status: "stale_policy"`, no rows) rather than re-deriving under the looser default — a looser policy covers more entries, so the panel would under-report "in your ledger, not on this statement". ADR: `docs/adr/2026-07-29-statement-instructions-as-deterministic-match-policy.md`.

**Ledger-check row projection** (`services/statements/ledger_diff._collect_uncovered`) — every entry in the "In your ledger, not on this statement" panel is `import_anomalies._existing_summary` (`note` = the row's `description`, plus amount/currency/category/account/original-charge) **plus two fields this module owns**, both resolved SERVER-SIDE so the import preview UI and the `import_transactions` tool read one answer (owner directive 2026-07-31: *"please handle these on the backend, not client so the ai tool can get the same information"*). (1) **`on_statements`** (`services/statements/ledger_statement_links.py`) — which statement(s) the entry is ALREADY on, as `{label, reference, statements: [{statement_id, label, filename, reference, period_start, period_end}]}`, or `None` when it is on none we hold. **Resolved from `external_refs`, NOT from `import_batch_id`** — the two answer different questions (*what is it on* vs *where did it come from*), and a merge never stamps `import_batch_id`, so the batch link is structurally blind to every row a statement LINKED rather than created. Measured on the owner's book: 355 rows are on a statement by refs, **116 of them invisible to the batch link** (one statement created 0 transactions and linked 46); where both resolve they never disagree (239/239). The reverse `ref → statement` index is built ONCE per panel computation by re-deriving each cached `import_rows` row through the importer's own `external_ref`, so it cannot drift from what a commit wrote; a record with no cached parse contributes nothing (74 of 81 records predate the decision pipeline). **A row can be on several statements** (24 on this book): `statements` is ordered — the cycle whose printed period CONTAINS the row leads, then the latest-closing — and `label` carries the "+N more" so the client never counts. `reference` is the BANK's own reference parsed out of `ref:<account_id>:<reference>`, `None` when the ref is instead our 24-char content hash (a dedup key, not a reference) — the opaque account id is always stripped, matching `TxnDetail.CHANGE_FIELD_HIDDEN`, which classes `external_refs` as internal bookkeeping. (2) **`near_cutoff`** — `{edge: start|end, days, label}` or `None`. **It is not a second threshold**: `_near_cutoff` returning non-`None` is *by construction* the predicate that files the row under `boundary` rather than `rows` (`(d − lo).days < boundary_days` or `(hi − d).days < boundary_days`, the same comparison the bucketing used to spell out inline), so `boundary_days = 0` on a self-referential window switches the flag and the bucket off together. The frontend renders both labels verbatim and derives neither — its old client-side `date > period.end` edge test was dead code, since `period` on the wire is the already-widened window no emitted row can fall outside.

**Statement metadata: `meta_unavailable` separates "unknown" from "absent"** (`services/statements/canonical.StatementMeta`) — `extract_meta_from_text` used to swallow ANY exception into an empty `StatementMeta` + a warning string, so a transient provider error (`529 Overloaded`, live 2026-07-31) cached as though the statement simply printed no header. Because the parse is cached and never re-billed, the record was then stuck: `ledger_diff._window` fell through to its rows-derived fallback (so the **ledger-check window itself was wrong**, which decides which entries the "not on this statement" panel collects at all), `_window_is_self_referential` was true so `boundary_days` collapsed to `0` and no `near_cutoff` could fire, and `_suggest_account` had no printed digits so the record bound to no account. Contrast the SAME file: row extraction RAISES on a provider failure (parse fails loudly, nothing cached). Three changes: (1) the metadata call gets a bounded retry (`_META_ATTEMPTS = 3`) — rows don't need one because they fail loudly, meta does because a blip is otherwise permanent; (2) on exhaustion the failure is recorded AS a failure (`meta_unavailable=True`), under which **every null field is UNKNOWN, not absent**; (3) `decisions._heal_cached_meta` — the third heal in the `_heal_cached_last4s` family and the only one that spends a call — re-extracts the text DETERMINISTICALLY from the retained file and re-runs the ONE bounded metadata call, **never re-reading the rows** (a metadata failure says nothing about them), landing before `_suggest_account` so recovered printed digits also re-detect the account. Gated on the FLAG, never on emptiness: a statement that genuinely prints no metadata is a legitimate all-null meta and must not buy a call on every preview, forever; a heal that fails again stays flagged rather than downgrading "unknown" to "absent". The heal is billed onto the file like the hint batch. One-shot migration for pre-flag records: `backend/scripts/migrate_statement_meta_unavailable.py` (stamps the flag off the legacy warning string, dry-run default, idempotent) — rather than teaching the heal to sniff for that string, which would be a back-compat shim and string-matching as control flow. ADR: `docs/adr/2026-08-01-failed-statement-metadata-is-recorded-not-cached-as-fact.md`.

**Staged ledger deletes ride the import commit** (`decisions.decision_commit(..., delete_ids=[...])`) — the "In your ledger, not on this statement" panel's `Delete` is a local MARK, applied at Confirm with every other decision, not a write-through `DELETE /api/transactions/<id>` per row (which broke the footer's own "nothing is written until you confirm" promise, was irreversible before commit, and reached the generic endpoint with no statement context and therefore NO guard). The ids are validated against this statement's re-derived **uncovered set** (`_manual_link_ids`) — the same set a manual link is validated against, and the reason the deletes live at this choke rather than in a client loop: only `decision_commit` can re-derive it. The caller's list is a REQUEST, never an authorization (the merge guard's posture). Both refusals happen **before any write**, so a bad list cannot half-apply an import: an id outside the uncovered set RAISES, and so does an id that is also a merge target in the same commit (an entry cannot be both linked and deleted). The guard is checked pre-commit deliberately — once the creates land, this statement's own new rows are in the ledger and the uncovered set is no longer the one the user reviewed. Execution runs **LAST**, through `ledger_service.bulk_delete_transactions` (soft-delete, one batched audit event, atomic refusal of a Starting Balance row), so a delete failure never costs the user the import they confirmed; failures are REPORTED in `delete_errors` (the `merge_errors` contract), surfaced on the Done screen — "delete 8" must never quietly become "deleted 7". An id already soft-deleted between preview and commit is NOT a guard breach (intent already satisfied): dropped from the batch, reported as `already deleted`. Frontend state is `pendingDelete`, deliberately NOT the retired `checkRemoved` (which meant "gone from the ledger" — a fact, not an intent). ADR: `docs/adr/2026-08-01-staged-ledger-deletes-at-the-import-commit.md`.

**Statement-close drift** (`services/statement_drift.statement_drift`, `GET /api/statements/drift`, `check_statement_drift`) — compares each statement's printed `import_meta.closing_balance` against `account_balance_as_of(statement_date)`, i.e. the ABSOLUTE balance. This is a different question from `verify_statement_balance`, which compares an import's NET CHANGE to the statement's own opening→closing delta and is therefore correct even when the opening is wrong — the blindness that let a S$4.75 opening error survive three weeks. Comparison is in the account's own currency (legs are stored that way); a statement stating a DIFFERENT currency is skipped, not converted. Sign: a liability prints positive what the ledger folds negative, so the fold is multiplied by `_bank_sign`. Three ordered verdicts, each narrowing the next. (1) **Is it an error at all** — a charge dated on the cutoff day that the bank posts after it makes the ledger legitimately run ahead, and such drift CLEARS at the next close, so `resolved_at_next_close` demotes it to `timing_only` and it does not count against `clean`. Verified on a production book: one close was off by exactly the single row dated on its own cutoff day and reconciled to 0.00 at the next close, which is what distinguishes lag from loss (a same-magnitude coincidence at a different account's close did NOT survive this test — the cause there was a manual balance-adjustment plug, so amount-matching alone is not evidence). Without this the check fires on nearly every card with a charge near its cutoff, and a check that cries wolf is one nobody reads. On the NEWEST statement lag and a missing row are indistinguishable, so the account reports `pending` rather than guessing. (2) **Was it there from the start** — `constant_drift` (identical drift at every unreconciled close) means the opening, but ONLY if the EARLIEST checked close is itself drifting: a clean earlier close proves the opening was right at that date, so blaming it would send the owner to fix the one number already correct. (3) **Otherwise where** — `drift_change` + `window_from` name the window between two closes that introduced it. A statement whose metadata read FAILED (`meta_unavailable`) contributes nothing rather than a null-derived zero; skips are counted, never hidden (the large majority of records on a production book print no closing balance, so coverage is genuinely thin). Reads only — it never edits and never decides which side is right. ADR: `docs/adr/2026-08-05-statement-close-drift-check.md`.

### `tool_permissions` — THE permission table for every tool (revision 0039 as `connector_tool_permissions`, absorbed + renamed at revision 0040)

**The first table added AFTER the JSON→DB migration finished — DB-native, no `.json`
ancestor, no cutover.** The Connectors redesign (§4; design handoff §10) landed it (revision
0039) as `connector_tool_permissions`, gating every connector lane — Channels, Data sources,
Web AND MCP, no exceptions — at one of three levels, nothing structurally locked out of the
top one (the `is_money_movement` floor and the MCP server-level `trusted` flag were removed
in the same lane — ADR `2026-08-13-mcp-permission-config-is-the-single-authority`).

**Revision 0040 absorbed `tool_grants` and renamed the table.** Until then the app had TWO
stores answering "may this tool run": this one (three levels, per connector, consulted only
by external-MCP dispatch) and `tool_grants` (binary grant/no-grant, per tool NAME, written by
the confirm card's "Always allow" and Settings › Permissions, consulted for everything else).
They could disagree with no way for the user to tell which had won. 0040 folds `tool_grants`
into this table under the reserved owner bucket `core` (a stored `scope: "always"` grant
becomes a `level: "always_allow"` row; an absent grant stays absent — absence is not a
decision) and deletes `tool_grants`, at which point the `connector_` prefix was simply false,
so the table is renamed `tool_permissions`. **The three levels are renamed in the same
revision**: `allow` → `always_allow`, `ask` → `needs_approval`, `block` → `blocked` — still
one uniform default (`needs_approval`) for an absent row. ADR
`2026-08-14-one-permission-store-for-every-tool`.

**Shape.** Generic `payload_table()`, Tier-3 (no `book_id` — a permission is this
INSTALLATION's trust posture, `tool_grants`' own tenancy): ONE row per (owner, tool) pair a
human actually decided about, `id = f"{connector_id}:{tool}"` (a deterministic surrogate,
`budget_assignments`' precedent), payload `{id, connector_id, tool, level, updated_at}`. The
`connector_id` column (name kept across the rename) is the tool's OWNER, not necessarily a
connector: its `@tool(connector=...)` id, `mcp:<server_id>` for an external-MCP tool, or the
reserved bucket `core` (`services.tool_permissions.CORE_CONNECTOR_ID`) for everything else —
`add_transactions`, the ~160 unscoped write tools (`send_email`/`search_messages`/
`get_messages` moved OUT of this bucket onto `connector="email"`, 2026-08-17). **The group aggregate is
DERIVED and has nowhere here to live** — "Custom" is "these tools disagree", computed at
display time by `services.tool_permissions.derive_group_level()`; a group-level pick is a
deliberately LOSSY stamp onto every tool in the group, in ONE transaction (a half-stamped
group would read as Custom — the state the user just acted to leave). ABSENT = `DEFAULT_LEVEL`
(`needs_approval`) for a connector-owned tool; an unset `core`-owned tool instead falls back to
the approval model's own read/write verdict (`ai.tools._confirm_gate.effective_level`) rather
than to `DEFAULT_LEVEL` — the one asymmetry that keeps every untagged tool behaving exactly as
it did before this table existed. `clear_connector_permissions` (delete the rows) stays
distinct from "decide on `needs_approval`" (write it explicitly).

**Enforcement is now universal.** `effective_level()` (`ai/tools/_confirm_gate.py`) is the
ONE dispatch-time read, consumed once in `registry.dispatch`, for every tool of every
connector AND every unscoped tool, native and MCP alike. The former
`tool_permissions.is_enforced()` predicate — true for `mcp:<server_id>` only — and the
`enforced`/`permissions_enforced` fields it rode on (the REST response,
`get_connector_permissions`, `ConnectorView.permissions_enforced`, the "not enforced yet"
notice in the Connectors UI) are REMOVED: there is only one answer, "yes", so there was
nothing left to report. `tests/test_get_tool_permission_has_exactly_one_production_caller`,
which pinned the old single-caller fact, is retired with it.

**Classification — `tool_grants`' four flags, verbatim** — both merged predecessors
classified identically, which is one more sign these were always one store wearing two names
(ADR `2026-08-13-connector-tool-permissions-storage`): checkpoint-EXCLUDED
(`restore_checkpoint` is model-callable with `mutates=("*",)`, so an included table would let
*block a tool → the model restores an earlier checkpoint → the block is gone* escalate
privilege through an unrelated tool); NON_RESTORABLE (`core.sensitive`, same argument against
a DR restore); NOT secret (decisions, not credentials); NOT portable and never `BRIDGED`
(instance-local trust must not travel in a backup) but wipe-only reachable by `/api/reset` —
"reset means reset", and the direction of that wipe is back to the cautious default. It is
the first non-restorable dataset with no `NON_RESTORABLE_FILES` twin, so
`tests/test_sensitive_paths.py`'s file→table drift guard grew a third category
(`db_native_non_restorable`) rather than being weakened to a non-exhaustive check.

**Migration (0039) carries `deny` across and refuses to carry absence.** The backfill reads
`mcp_clients.payload → tool_permissions` (the old MCP-only, two-valued, opt-in-DENY map): a
stored `"deny"` becomes `block` under `mcp:<server_id>`, a stored `"allow"` becomes `allow`
— but an ABSENT entry is NOT backfilled as `allow`, including on a `trusted` server, because
absent now means `ask` and a permission migration may only move in the cautious direction
(both spellings are revision-0039-era; 0040 renames the stored values on top, unconditionally,
after this backfill has already run). `McpServerConfig.tool_permissions` itself is untouched
by revision 0039; retiring the field belongs to the dispatch lane that rewires
`mcp/client_manager.py` to read `services.tool_permissions` directly (done ahead of 0040 — see
`backend/mcp/client_manager.py`).

**REST.** `GET|PUT|DELETE /api/tool-permissions[/{tool}]` (`api/tool_permissions.py`) is the
Settings › Permissions surface, replacing the deleted `/api/grants`. The connector-scoped
`GET|PUT|DELETE /api/connectors/{id}/permissions[/{tool}]` (registered BEFORE
`connectors_api`'s `{connector_id:path}` route — order is load-bearing) is unchanged in shape,
now speaking the renamed levels and carrying no `enforced` field.

**Revision 0043 (2026-08-17, security-review follow-up)** is a second forward-only DELETE on
this table, no schema change: after `send_email`/`search_messages`/`get_messages` were tagged
`connector="email"` (fixing an owner-resolution mismatch — an `email`-owned row from the
connector's own ladder was written but never consulted at dispatch, which read the untagged
tools as `core`-owned instead), the fix alone would have made any pre-existing row under
either the stale `email` key (written, never enforced) or the now-reinterpreted `core` key
(enforced, but never specific to email) suddenly REAL — silently activating or degrading a
permission with zero new operator action. The migration drops exactly the six possible
`{core,email}:{send_email,search_messages,get_messages}` rows; nothing an operator actually
experienced as enforced is lost, since neither key was ever simultaneously written-to and
consulted before the fix. ADR
`2026-08-17-connector-ladder-shows-the-real-effective-default`.

**Four tiers (D5).** **Tier 1** — relational, typed columns, `book_id` — the money core (accounts, transactions, positions, lots, …); cut over in Plan 3 (the money core, stage-3) and Plan 4b (the investment stores) — see below. **Tier 2** — `(id PK, <promoted indexed columns>, payload JSON, created_at)`, world/reference data and append-only logs, **no** `book_id` (identical for every user and book): `evidence` is the first store cut over here. **Tier 3** — installation settings (auth, model/connector config), no `book_id`. **Tier 4** — files stay files: skills, uploads, statement source documents, artifacts, app logs, `CACHE_DIR` — the database holds records you query/join/keep transactionally consistent, the filesystem holds opaque bytes fetched whole, by name. No BLOBs in the database.

**Identity, seeded 1/1/1 (D4).** `users` / `books` / `book_members` (role: owner|member|viewer) were created in Alembic revision `0001`, ahead of any store cutover, seeded with exactly one deterministic-sentinel row each (`usr_000000000000`, `book_000000000000`, owner) — not random ids, so QA clones/fixtures/round-trip diffs stay reproducible across installs. `book_id` lands on Tier-1 tables ONLY, as each is cut over (retrofit-cost asymmetry: one column + one base-class filter now vs. a whole-ledger migration later); hosted mode mints ordinary random ids for new rows, which can never collide with the all-zeros sentinels. ADR `2026-08-07-book-partition-key-and-identity-seeded-1-1-1`.

**The cutover ledger.** `json_cutovers (store PK, source_path, source_hash, migrated_at, renamed)` records which JSON files the database has absorbed. The importing revision INSERTs a row (with the source file's sha256) inside its own transaction, after an exact round-trip re-export of every imported row is diffed against the original file — any mismatch raises and aborts the whole migration (never a partial absorb). The source file is renamed to `<name>.json.migrated-<ts>` — **never deleted** — only AFTER `upgrade head` fully succeeds, and only if the file's hash still matches what was absorbed (a source that changed after being read refuses the rename rather than silently losing the newer bytes); each store's rename+flag commits in its own transaction so one store's failure can't roll back another's already-completed cutover. Boot wraps all of this fail-closed: `db/migrate.ensure_migrated()` (first call in `lifespan`) takes a verified backup, runs `upgrade head`, and on ANY failure restores the backup and refuses to boot. ADR `2026-08-07-fail-closed-alembic-migrations-with-verified-backup`.

**`evidence` table shape (stage-1 cutover, `backend/db/evidence_store.py`).** `evidence (id PK, seq, expires_at, domain, created_at, payload JSON)` — `payload` is the VERBATIM row and the only thing a round-trip export reads (Postgres `json`, deliberately not `jsonb`, which would normalize key order against that fidelity guarantee); `expires_at`/`domain`/`created_at` are derived indexes recomputed from `payload` on every write; `seq` is assigned explicitly (SQLite has no non-PK autoincrement) to preserve the source file's original insertion order portably across dialects. `evidence_subjects (evidence_id, subject)` is the child table behind `for_subjects()`'s tag lookup, `ON DELETE CASCADE`d with its parent. Mutating calls (`merge_hits`, `prune`) hold a module-level `threading.Lock` for the same in-process concurrency guarantee the old per-path `JsonStore` lock gave — ADR `2026-08-07-evidence-store-write-serialization`. **Verified at production scale** (2026-08-07 dress rehearsal, run against a clone of the real data under `/tmp`, never the live tree): 86,145 real evidence rows / ~111.4 MB source JSON migrated in 3.4s with a clean round-trip verify, landing a ~164.7 MB `onw.db`; `count()` returns in ~1ms; a real selective-tag `for_subjects()` lookup (10,983 matching rows of 86,145) measured 142ms, and a non-matching subject returns in ~1ms. A near-universal tag is slower than a full scan (83,391/86,145 rows: ~2.1s vs. `all()`'s 0.6s) — acceptable for Intel's access pattern, revisit if it grows.

**`price_points` — real relational columns, not a payload blob (stage-2 cutover, `backend/db/price_history_store.py`, plan 2 task 3).** Unlike `evidence`'s generic `(id, payload)` shape, this store's data genuinely IS rows: `price_points (price_source_id, date, price FLOAT, source)`, composite PRIMARY KEY `(price_source_id, date)` — the store's "one point per (instrument, day), last write wins" invariant is now DB-ENFORCED (a write is a delete+insert on that key, never a duplicate row), where the pre-cutover JSON store hand-rolled the same dedup on every save. `PriceHistoryStore` keeps its exact pre-cutover public surface (`series`/`latest`/`latest_map`/`prior_to`/`prior_to_map`/`as_of_maps`/`earliest_date`/`latest_date`/`record`/`record_many`/`record_backfill_series`/`prune`) — every caller across `services/`/`ai/tools/` is unchanged. **NOT checkpoint-captured**: `price_points` sits in `ai.checkpoint._EXCLUDED_TABLES` (parity with the pre-cutover store, whose `_save` never fired the file write-hook either — append-only market-cache data, not per-turn AI state) and is additionally guarded STRUCTURALLY — its composite PK means it could never pass `write_log`'s single-PK guard even if the exclusion were revisited later (ADR `2026-08-07-write-log-row-level-checkpoints`). One process-wide `threading.Lock` serializes every mutating method's full read→modify→write cycle (the Plan-1 `EvidenceStore` pattern: there is only one table, so "per path" collapses to "one lock"). **Parity-verified at production scale** (2026-08-07 dress rehearsal 2, a `/tmp` clone, live tree untouched): 34,424 real price points across 196 series (~3.2 MB source JSON), absorbed in the same migration run as the other two stores below; `as_of_maps` spot-checked against the RETIRED pre-cutover implementation (invoked from git history, `git show 3200b3a2:backend/db/price_history_store.py` — `3200b3a2` is `07ed76bd^`, the cutover commit's direct parent and therefore the file's TRUE last pre-cutover state, confirmed via `git rev-parse 07ed76bd^`) on 3 sampled dates (2022-12-31 / 2024-06-30 / 2026-07-31) plus `latest_map()` across all 196 series — EXACT equality, zero mismatches, re-verified in task 8's fix round 1 against a fresh minimal clone after the initial report cited an unreachable SHA from a divergent branch. **`latest_map()`/`prior_to_map()` are index-backed aggregates** (2026-08-10): a `MAX(date)`-per-instrument GROUP BY over the composite PK, NOT a whole-table `ORDER BY` folded in Python — byte-identical to the scan (`MAX(date)` per pid IS "last write wins", the PK is unique), but it fetches one row per instrument instead of the whole table. This was the dominant source of the app's tab-load contention (every hot-path hydration full-scanned ~200k price points for ~200 values); fixing the over-fetch, NOT rewriting money math as SQL or adding workers, is the recorded perf posture — ADR `2026-08-10-perf-is-over-fetch-not-sql-or-workers`. `as_of_maps` still scans (net-worth history needs every point).

**`instruments` — the first `PayloadTableStore` (stage-2 cutover, `backend/db/instrument_store.py`, plan 2 tasks 4–5).** `PayloadTableStore` (`backend/db/payload_store.py`) is the generic JsonStore-surface base every remaining flat-list store (Plans 3–4, ~40 stores) subclasses from here on: a `payload_table(name)` factory registers `(seq INTEGER, id TEXT PK, payload JSON)` + a unique `seq` index on the shared metadata, and the base class supplies the full JsonStore-parity surface (`all`/`find_by_id`/`query`/`count`/`insert`/`bulk_insert`/`upsert`/`update_by_id`/`bulk_patch`/`delete`/`replace_all`) over it — **table + revision + subclass + importer is the whole recipe for a new store from here on.** `instruments = payload_table("instruments")` (Alembic `0005`, `down_revision="0004"`) absorbed the pre-cutover flat JSON list (`root_key=None` — the revision ABORTS rather than silently coercing if the source file is ever anything but a top-level list). `InstrumentStore(PayloadTableStore)` keeps every domain method verbatim (`find_by_source`/`find_by_symbol`/`find_by_symbol_and_class`/`find_by_identifier`/`query_instruments`/`create`/`find_or_create`/`touch`/`set_constituents`) as `all()`-scans, exactly as they ran over the JSON file — this cutover does not "optimize" any of them into SQL. **CHECKPOINT-INCLUDED** (`checkpointed=True`, the base class default) — the FIRST DB-backed store proven in the `/rewind` contract: every mutate collects each touched row's before-image and fires it through the caller's own transaction via `core.io.fire_db_write_hook` (see `write_log` below), so an AI turn that edits an instrument is undoable exactly like a JSON-store edit always was. Concurrency: one `threading.Lock` PER TABLE NAME (a registry, since one `PayloadTableStore` subclass backs many distinct tables, unlike `EvidenceStore`/`PriceHistoryStore`'s single hard-coded lock) — the registry itself lives in `backend/db/engine.py` as of Plan 3 task 1 (moved from `payload_store.py`, which already imports `engine.get_engine()`, to avoid an import cycle with the new `locked_unit_of_work` below), `payload_store.py` just imports `_lock_for_table` from there. **The choke-point composition seam (Plan 3 task 1):** every mutate above also accepts a trailing `conn: Connection | None = None` — `conn=None` (every call site through Plan 2) is unchanged; a caller composing a multi-store money write instead opens `backend.db.engine.locked_unit_of_work(*tables)` (acquires every composed table's lock in ONE global alphabetical order, then one transaction) and passes its connection into each mutate, which then skips its own lock/transaction since the caller already holds both. This is the seam Plan 3 task 4's ledger chokes (accounts + transactions, one transaction) build on; proven deadlock-free by a two-thread, opposite-lock-order test (`tests/db/test_choke_seam.py`) before any real caller exists yet. **Verified at production scale** (dress rehearsal 2): 58 real instruments absorbed; a live `begin_turn` → `InstrumentStore().touch()` on a real absorbed instrument → `end_turn` → `restore` round-trip proved the touched field reverted to its exact original value — the first end-to-end `/rewind` proof on a DB-backed store, on real data.

**The money core — eight tables, one referential unit (stage-3 cutover, plan 3 tasks 2–4).**
`accounts`, `transactions` (+ children `transaction_splits`/`transaction_external_refs`),
`txn_audit`, `import_batches`, `statements_meta`, `merge_journal` — absorbed off their six source
JSON files as ONE unit (revision 0007; a dangling `opening_txn_id` or a dangling account ref aborts
the WHOLE absorb, never a partial one). Every table carries `payload JSON NOT NULL` (the round-trip
source of truth) PLUS promoted query-surface columns recomputed from it on every write — including
`transactions`/`transaction_splits`/`transaction_external_refs`, which the original plan called
fully-promoted-no-payload until live data proved the difference matters: `created_at` is genuinely
absent (not merely falsy) on 68 of 1,816 real transaction rows, `memo` on 1,228 of 1,816, and 86 of
87 real statement rows carry their batch linkage under a dead, unrenamed key (`import_batch_ids`)
rather than the promoted column's own name — a promoted-only column cannot tell "absent" from
"empty" and would silently invent a value for one. `book_id` leads every non-PK index (Tier-1
partition key). `from_account_id`/`to_account_id` are `ForeignKey("accounts.id",
ondelete="RESTRICT")` — the `delete_account` 409-while-referenced invariant is now DB-enforced
(force-cascading past it hard-deletes the referencing rows first, in the same transaction — ADR
`2026-09-06-force-delete-account-hard-removes-its-cascaded-transactions`);
`transaction_splits`/`transaction_external_refs` FK `transactions.id` `ondelete="CASCADE"`.
`opening_txn_id` (accounts) and `merged_into` (transactions) carry NO FK — both are
circular-reference hazards the services layer already owns (the dangling-RAISES-but-repairable
contract for the former; a transient mid-tombstone pointer during merge/undo for the latter). **No
`STRICT` tables** — a deliberate deviation from the design spec's original Tier-1 line: `STRICT` is
SQLite-only DDL, and the program's own no-dialect-specific-SQL discipline outranks it; typed columns
+ portable `CheckConstraint`s (`transfer_has_both_legs`, four boolean `IN (0,1)` checks) + `NOT
NULL` deliver the same integrity. `transaction_external_refs`'s `(book_id, source, ref)` index is
deliberately non-unique — a legitimate merge duplicates a pair across two live rows (ADR
`2026-08-07-external-ref-index-non-unique`). ADR
`2026-08-08-money-core-tables-verbatim-payload-plus-promoted-columns`.

**Money storage is exact decimal TEXT; arithmetic stays float (revision 0008, plan 3 task 5).**
Seven columns (`transactions.{from_amount,to_amount,base_amount,fx_rate,original_amount,quantity}`,
`transaction_splits.amount`) convert `Float`→`Text` holding `repr(float)` — the shortest decimal
literal guaranteed to round-trip exactly (`float(repr(x)) == x`). Verified inside the migration,
all-or-nothing: per-row `float(new_text) == old_float` exact, plus a per-BOOK `Decimal`-summed
signed invariant on `base_amount` (never float-summed, so the check itself cannot hide a rounding
drift), symmetric on downgrade. Two real dialect hazards were found by actually running both
dialects, not assumed from documentation: SQLite's batch-recreate (its only type-ALTER mechanism)
fires `ON DELETE CASCADE` on `transaction_splits`/`transaction_external_refs` the instant
`transactions` itself is recreated, silently wiping both child tables unless their rows are dumped
via raw `SELECT *` and restored around the ALTER; Postgres requires an explicit `USING` cast. Store
reads return `float(text)` (bit-identical to a pre-migration float read); writes store
`repr(float(value))` — **the service-layer arithmetic type stays float**, a deliberate, deferred
future program (converting the ~3,000 lines of `services/` monetary math to `Decimal` is its own,
separately-verified effort — not started by this revision). ADR
`2026-08-08-money-stored-as-exact-decimal-text-arithmetic-stays-float`. **Parity-verified at
production scale** (2026-08-08 dress rehearsal 3, a `/tmp` clone, live tree untouched): the
pre-cutover stack (float JSON files, SHA `7be167c22c9b6762fb2def5f18642562d27c99d2`) and the
post-cutover stack (this Text-decimal DB, full chain 0001→0008) computed
`net_worth()`/`balances()`/`net_worth_history()` independently against identically-cloned real data
(29 accounts / 1,816 transactions / 5 splits / 824 external refs) — canonical-JSON output BYTE-
IDENTICAL (sha256 match, 3,154 bytes both sides). A live `/rewind` proof in the same rehearsal (edit
one transaction's `memo`, `begin_turn`→`update_transaction`→`end_turn`→`restore(mode="data")`)
reverted the row byte-exact against its pre-edit capture. Full evidence:
`.superpowers/sdd/2026-08-07-storage-plan3-money-core/task-8-report.md`.

transaction — every filesystem delete is collected during the wipe/import phase and only actually
unlinked AFTER a successful commit (`services.portability._unlink_best_effort`), and the collected
delete-set is re-checked against the LIVE `has_parsed_rows` set (deriving each surviving row's path

its own transaction's deferred cleanup. Separately, the
absorb (task 3) found `PRAGMA foreign_keys=ON` was NOT actually active during any Alembic
migration's own connection (a different, listener-less engine instance than the app's runtime one)
— `backend/db/alembic/env.py` now reuses `db.engine._make_engine`, so every SQLite migration
connection enforces real FKs exactly like the app's own runtime engine does. ADR
`2026-08-08-money-core-choke-points-become-one-transaction`.

**`write_log` — row-level checkpoints for DB stores (spec D7, plan 2 task 2; replay/GC hardened in the Plan-2 final-review wave; restore itself hardened fail-closed + staged-file in Plan 3 task 1).** Replaces whole-file gzip blob snapshots for every DB-backed store: `write_log(checkpoint_id, seq, table_name, pk, before_payload JSON NULL, created_at)`, composite PK `(checkpoint_id, seq)`; `before_payload = None` means the row did not exist pre-turn (replay deletes it). `core.io.fire_db_write_hook(table_name, rows, conn=None)` is the seam (mirrors the pre-existing file write-hook, `core/` stays a stdlib leaf); `ai.checkpoint.CheckpointContext.record_db_before` captures the FIRST before-image per `(table, pk)` per turn, inserted immediately and durably (crash parity with file blobs — the row exists even if the turn never reaches `finalise()`) — THROUGH the caller's own open transaction when one is passed, and that insert runs inside a SAVEPOINT (`conn.begin_nested()`): the first genuine Postgres run of `tests/db` (see below) found that a bare `conn.execute` there let a swallowed write_log failure abort the CALLER's whole transaction on Postgres only (SQLite tolerates a failed statement mid-transaction; `automation_runs` is the ONE Tier-2 logs table deliberately left OUT, checkpoint-INCLUDED; plan 4d task 1 added `tool_grants`/`signals` (renamed `notification_log` at revision 0044) — see the config-stores paragraph above; every later wave through 5F plus the 2026-08-14 permission merge kept adding to this set, so **the literal membership is NOT reproduced here — read `backend/ai/checkpoint/_policy.py::_EXCLUDED_TABLES` directly, since a copy pasted into prose goes stale on every future wave and already has: `tool_grants` was absorbed into `tool_permissions` and deleted at revision 0040, and the set gained roughly a dozen more entries — `pending_pushes`, `checkpoints`, `tool_discovery_log`, `cost_log`, `cost_log_daily`, `agent_findings`, `runtime_state`, `secret_config`, `mcp_clients`, `artifacts`, among others — that this paragraph never tracked**) is the DB mirror of `_EXCLUDED_PATHS`; a checkpointed table's primary key MUST be a single column — enforced TWICE: at replay (`_single_pk_col`, raises loudly on a composite PK rather than silently corrupting unrelated rows) and, since the final-review wave, at `PayloadTableStore.__construction__` time too (`checkpointed=True` on a composite-PK table refuses immediately, mirroring `_single_pk_col`'s message — `db` duplicates the check rather than importing `ai`). **Restore order is binding**: `_capture_pre_restore_snapshot` captures BOTH worlds' current state first (so the restore is itself undoable, same as files — its DB half is FAIL-CLOSED since Plan 3 task 1: `_capture_db_pre_restore` passes `record_db_before(..., fail_closed=True)`, so an image that cannot be recorded aborts the restore before anything is touched instead of letting a silently-incomplete undo snapshot go on to be mutated behind) → `_replay_write_log` — ONE transaction, reverse-`seq` order, **TWO-PHASE since the final-review wave**: phase 1 deletes every row the checkpoint touched (by pk, including the `before_payload = None` ones), phase 2 re-inserts every non-None before-image — a single interleaved delete-then-insert PER ROW (the original shape) collided on a table's unique `seq` index whenever a turn's write PERMUTED row order (e.g. `PayloadTableStore.replace_all([b, a])` on a table that had `[a, b]`); splitting the phases makes row order irrelevant — runs BEFORE any file write, so a DB replay failure aborts the whole restore with nothing partially reverted across the two worlds → files STAGE to a temp path (`<dest>.restore-tmp-<checkpoint_id[:8]>`) before the replay call and only RENAME into place after it succeeds (`_stage_restore_files`/`_commit_staged_restore_files`, Plan 3 task 1 — shrinks the split-world window from the whole read-blob→decompress→write sequence down to that final rename loop; a replay failure after staging unlinks the temps, a crash inside the rename loop leaves an untouched destination beside its fully-staged temp and a re-run of `restore()` finishes the job). **GC pinning**: a module-level `ai.checkpoint._pinned_ids` refcount (`collections.Counter` since Plan 3 task 1 — a plain set's `discard` let the FIRST unpin release an id a second concurrent holder, e.g. an overlapping restore of the same checkpoint, was still relying on) protects (a) a turn's own checkpoint id for its full `begin_turn`→`end_turn` span (an in-flight turn's write_log rows are durable before it has an index entry to protect them) and (b) `restore()`'s own target id plus its pre_restore snapshot's id for the restore's duration (capturing the pre_restore snapshot finalises a new checkpoint whose OWN prune must never evict the checkpoint being replayed) — without this, restoring the OLDEST of `MAX_CHECKPOINTS` active checkpoints silently reverted nothing (the pre_restore append pushed the target past the cap, mid-restore), and a concurrent session's prune at cap could delete an in-flight turn's rows out from under it. `write_log` rows are GC'd alongside blob GC (`_gc_write_log`/`_gc_blobs`, same `MAX_CHECKPOINTS = 50` retention, best-effort, pinned-id-aware, and — since Plan 3 task 1 — `_gc_blobs` logs any blocking pin id(s) at WARNING when it defers, so a leaked pin is discoverable instead of a silent, permanent GC stall). `_db_preview_rows` fails LOUD (raises) on a table the checkpoint touched but which no longer exists, matching `_replay_write_log`'s pre-existing loud failure there, instead of silently omitting the row from the preview panel. The checkpoint INDEX itself (which checkpoints exist, their manifests) stayed a JSON file through this plan (Plan 2) — its own cutover landed later, onto the `checkpoints` table (see the Wave E paragraph above). ADR `2026-08-07-write-log-row-level-checkpoints` (mechanism, with the Plan-2 final-review wave's replay/GC/transaction fixes AND Plan 3 task 1's restore-hardening/refcount fixes both recorded as dated Amendment sections on that same ADR — bug fixes and hardening to an already-decided mechanism, not fresh decisions).

**`tests/db` is the dialect contract** (Plan-1 final-review recommendation 4, written down here per that review). Every new table/store's test belongs under `tests/db/` — that directory, and only that directory, is what the Postgres CI job (`.github/workflows/ci.yml`'s `db-postgres` job) runs against both dialects. A store test placed elsewhere (e.g. beside the service that consumes it) is SQLite-only by construction, silently losing the Postgres coverage the job's existence implies every DB-backed store has. Practically: `tests/db/conftest.py::db_isolated` is what binds a test to an isolated, freshly-migrated database in either dialect — only tests importing it get exercised on both. **This was a false promise until the Plan-2 final-review wave (2026-08-07, C1):** `db_isolated` hardcoded its own `sqlite:///{tmp_path}/test.db` URL instead of consuming the `db_url` fixture (which honors `ONW_TEST_DATABASE_URL`), so the `db-postgres` CI job ran genuinely green while silently exercising SQLite for every one of the ~100 test functions built on `db_isolated` — only the smaller set built directly on `db_engine` (migrations, evidence I/O) was ever actually dialect-tested. Fixed by making `db_isolated` consume `db_url` and perform the same `DROP SCHEMA public CASCADE; CREATE SCHEMA public` scrub `db_engine` already did on Postgres. **First genuine run, post-fix:** the full `tests/db` suite (137 tests, including the fixes' own new regression tests) against a real `postgres:16` container — 136 passed on the first try; the 137th (a new regression test written specifically to probe the swallowed-write_log-insert/SAVEPOINT divergence above) failed exactly as predicted pre-fix and passes post-fix. That was the one real dialect divergence this wave's Postgres run surfaced.

**`sql_query_log` (revision 0050, read-only SQL access, 2026-08-23) — the audit ring for Lucius's direct database reads.** DB-native (no `.json` ancestor, no cutover), created by `docs/superpowers/specs/2026-08-23-lucius-sql-access-design.md` alongside the `run_sql_query`/`describe_db_schema` tools. Plain `payload_table()` shape and the same Tier-2 classification as the thirteen logs/telemetry tables from Plan 4c and Wave 5B: NO `book_id` (an operational record of what was asked of the database, not book-scoped user data), checkpoint-EXCLUDED (`ai.checkpoint._policy._EXCLUDED_TABLES` — a `/rewind` undoes what Lucius did to your DATA, and a read did nothing to it; the record of what was ASKED is forensic), and — mirroring `tool_call_log` exactly — NEITHER a `db/portable_bridge.py` `BRIDGED` entry NOR a `_WIPE_FNS` one, since a runtime log has no export or reset role. Capped ring of `MAX_SQL_QUERIES = 500`, newest-first, evicting oldest — sized for the recent-history question this log answers ("what has it been asking, lately?"), not the multi-week trend analysis `tool_call_log`'s 5,000 exists for. Row: `{id, ts, sql, ok, error, row_count, truncated, elapsed_ms, origin, session_id, caveats}`, written by `services.sql_query.run_query` on EVERY attempt including refusals (the owner needs to see what it tried, not only what it managed), through a `_log` helper that swallows its own failure — losing one audit row is strictly better than turning a policy-allowed read into an error. **It stores the SQL VERBATIM** (capped at `MAX_SQL_CHARS = 4000`), a deliberate departure from `ToolCallLogStore`'s pinned "SIZES AND SHAPES ONLY — never raw arguments": for a high-volume telemetry ring the arguments are incidental and storing them would turn a log into a financial-record spill, but here the statement IS the auditable action — a row reading "a 412-character query returned 9 rows" tells an owner nothing about whether the capability is behaving. `McpWriteLogStore` made the same call for the same reason. Consequences of that choice, all load-bearing: the only reader is `GET /api/sql-queries` (auth-gated, `Cache-Control: no-store`, `backend/api/sql_query.py`), the Settings > Developer list is marked `data-ctx-secret` so a `WHERE` clause embedding real amounts or account names never rides into the Lucius screen snapshot, and NOTHING under `ai/` or `mcp/` reads the table back — it is written by the model's activity and read only by the operator. The executor it records (`backend/db/sql_console.py`) is the ONLY module in the codebase permitted to execute caller-supplied SQL; its denied-table set is `core.sensitive.SECRET_TABLES ∪ {sessions}`, REUSED rather than re-listed, and `tests/db/test_sql_console.py::test_every_table_is_classified_allowed_or_denied` fails if any table on `db.tables.metadata` is neither readable nor explicitly denied. ADR `2026-08-23-lucius-reads-the-database-directly`.

**`receipts` + `transaction_receipts` (revision 0042, cross-channel-attachments RFC Phase 4, 2026-08-16) — transaction evidence, independent of `attachments`/`statements_meta`.** ADR `2026-08-15-separate-attachments-receipts-and-statements.md` ("Transaction receipts") required durable receipt evidence with its own identity, bytes, and lifecycle, separate from both the chat-attachment catalog and the statement importer — a generic chat upload must never become "evidence" just by being uploaded, and a transaction may cite zero or more receipts while one receipt (a single itemized bill) may support more than one transaction. Two brand-new tables, schema-only (no prior JSON file to cut over, mirroring revision 0039's own shape): `receipts` — the SAME HYBRID `payload_table()` shape as `attachments` (metadata catalog in the DB; original bytes RAW — not base64-JSON-wrapped, since a receipt has no parsed-entry shape to preserve — under `RECEIPTS_DIR/<id><ext>`, `ext` safely derived from the row's `filename`/`media_type` via `core.file_ext.file_ext`; originally always `<id>.bin` regardless of type, fixed 2026-08-21 alongside `RECEIPTS_DIR` itself moving under the new shared `FILES_DIR = DATA_DIR / "files"` parent — see `docs/adr/2026-08-21-unify-raw-file-storage-across-blob-stores.md`), NO `book_id`; and `transaction_receipts` — the many-to-many LINK table `(id, transaction_id, receipt_id, linked_at, audit_context)`, also a bare `payload_table()` (no promoted `transaction_id`/`receipt_id` columns — `TransactionReceiptStore.by_transaction`/`by_receipt` filter Python-side, the documented default for this table's scale; a future hot lookup earns its own indexed column then, not preemptively). Both checkpoint-INCLUDED (reversed 2026-08-21 — see the amendment on ADR `2026-08-15-separate-attachments-receipts-and-statements.md`: `write_log` checkpointing is row-level and first-touch-per-turn, ADR `2026-08-07-write-log-row-level-checkpoints`, so a restore only ever replays the exact rows ONE turn wrote and cannot resurrect or relink a row a later turn touched — the same guarantee every other user-data table in this app already relies on) and portable/BRIDGED via the generic `misc_io`/`_misc_bridge` pair, identically to `attachments`/`artifacts` (portability is independent of checkpoint status). The write choke is `services.receipts.apply_receipt_change` (mirrors `services.equity.apply_equity_change`'s change-dict shape): `promote_from_attachment` (idempotent by `source_attachment_id` — re-promoting the same chat attachment reuses the existing receipt rather than duplicating it), `attach_existing` (the m:n case — link an already-promoted receipt to a second transaction), `unlink` (removes the link row only; the receipt survives), and `delete` (REFUSED — `ConflictError`, naming every linked transaction — while any transaction link exists, unless the caller passes `force=true`, per the ADR's "must never silently remove transaction evidence"). `promote_from_attachment`+`attach_existing` compose the receipt-row write and the link-row write in ONE `db.engine.locked_unit_of_work(receipts, transaction_receipts)` transaction when both happen together; `ReceiptStore.delete_receipt` follows the SAME rollback-safety contract `db/portable_bridge.py`'s `wipe_all` established (delete the DB row inside the transaction, defer the blob-file unlink to the caller, only AFTER that transaction commits — `conn=None` standalone calls delete the blob immediately, matching `AttachmentStore.delete_attachment`'s existing looser convention for the uncomposed case). Every attach/unlink records `core.audit_context.get_audit_scope()` onto the link row's `audit_context` field — the same ContextVar seam the ledger choke reads. `services.ledger.get_transaction` (the ONE detail read both `GET /api/transactions/{txn_id}` and the `get_transactions(transaction_id=...)` AI-tool branch share) now attaches a `receipts` array to its result — deliberately NOT added to the bulk `get_transactions` list path, to avoid an N-row extra query on every page. AI tool surface: `attach_receipt` (promote-from-attachment OR link-existing, one schema covering both — fail-closed per the RFC's clear-receipt rule: its description instructs the model to call it ONLY on explicit user intent or an unambiguous receipt it is using to create/identify the transaction, never on a guess), `unlink_receipt`, `delete_receipt` — all three `mutates=("receipts",)` — plus a fourth, READ-ONLY `read_receipts(receipt_ids: list[str], up to 10)` (2026-08-21): `services.ledger.get_transaction`'s own `receipts` array is METADATA only (filename/media_type/ids), so this is the tool that lets Lucius actually SEE a receipt's contents. It is the on-demand vision-read twin of `read_attachments` (`ai/tools/uploads.py`, RFC §5) pointed at `ReceiptStore` instead of `AttachmentStore`, sharing the SAME reader-routing core (factored out to `ai/tools/_vision_read.py::read_entry_via_configured_reader`/`log_on_demand_routing`) rather than inventing a second copy: every image/scanned-PDF receipt is read by the configured `chat_vision` extractor model REGARDLESS of the calling chat model's own vision capability (one reader policy, matching `read_attachments`' own documented reasoning — no per-call extraction-mode parameter to keep in sync), and a digital PDF with real extractable text is returned directly, no reader call. Since a receipt has no pre-parsed `kind` shape the way an `AttachmentStore` entry does (raw bytes only, `ReceiptStore.read_bytes`), `read_receipts` calls `services.attachment_parse.parse_upload` on the fetched bytes to get the same `text`/`image`/`pdf_pages` shape before handing it to the shared reader core. Explicit statement promotion (item 22, same phase): `StatementStore.create` gained a `source_attachment_id` keyword (recorded on both a fresh row and backfilled onto a dedup hit that doesn't have one yet) and `services.statements.decisions.decision_preview` threads it through from `import_transactions(attachment_ref=...)` — dedup is BY CONTENT HASH, already built into `StatementStore.create`, so promoting the same attachment twice is naturally idempotent; no new discriminator field was needed. `services.attachment_ingress.persist_inbound_file` — the ONE shared choke every chat channel (web upload, Telegram photo/document) already wrote through — no longer calls `StatementStore.create()` at all (item 21): a generic chat upload creates ONLY an `AttachmentStore` row now; `AttachmentStore`'s own `statement_id` field is REMOVED (it only ever existed to carry that unconditional coupling). **REST surface (2026-08-21):** `backend/api/receipts.py` mirrors the AI tool surface 1:1 for the transaction-detail drawer's Receipts section — `GET /api/transactions/{txn_id}/receipts` (the `receipts` array read), `POST /api/transactions/{txn_id}/receipts` (`attachment_id` xor `receipt_id` body, routing to `promote_from_attachment`/`attach_existing`), `DELETE /api/transactions/{txn_id}/receipts/{receipt_id}` (unlink only — the drawer never exposes `delete`, which stays chat-tool-only), and `GET /api/receipts/{receipt_id}/file` (raw bytes for the row thumbnail/in-app viewer). The file-serve route only ever serves `Content-Disposition: inline` for a fixed allowlist of real image/PDF media types — a receipt's `media_type` is the ORIGINAL upload's client-declared value, never sniffed, so anything off that allowlist (a spoofed type, an SVG) downloads as `application/octet-stream` instead of rendering same-origin.

**Derived-data colocation — one directory, one glob-delete, per blob store (revision 0046, consolidate-derived-data-storage RFC, 2026-08-22).** `.claude/rfcs/2026-08-22-consolidate-derived-data-storage.md` (Option A) states the rule every blob store now follows: everything a store keeps on disk for id `X` lives under `FILES_DIR/<store>/` and starts with `X` — `X<ext>` is the original, `X.parsed.json` is what was computed from it, one directory, no second location. Two stores broke that rule before this revision and both converge here. **Statements**: `statements_parsed/<id>.json` (a SEPARATE top-level directory, not even under `files/` — see ADR `2026-08-21-unify-raw-file-storage-across-blob-stores.md`'s own "deliberately stays OUTSIDE `files/`" line, revisited and reversed by this RFC once the SAME migration was found to have already put a derived-only payload inside `files/attachments/`, making the stated distinction one the tree didn't actually hold) moves to `FILES_DIR/statements/<id>.parsed.json`. **Attachments**: the already-colocated `<id>.json` derived-payload sidecar (`attachment_store.py`, unchanged since 2026-08-21) is renamed `<id>.parsed.json` — closing a latent collision hazard: today safe only because `.json` isn't in `core/file_ext.py`'s extension allowlist, so a raw upload can never overwrite it; adding `.json` there later would let a raw file overwrite its own derived sidecar. `StatementStore.delete_statement`/`AttachmentStore.delete_attachment` both now glob-unlink `<id>.*` in their one directory (statements gained this the same day attachments already had it, closing the SAME delete-completeness gap ADR `2026-08-21`'s security amendment closed for attachments once already). **The DB-column design question (the RFC's own §5 plan left this open, explicitly deferred to whoever implemented it — not a silent deviation from a stated RFC decision):** `statements_meta.parsed_rows_path` — a full, DATA_DIR-relative STORED path — is REPLACED by `has_parsed_rows` (Integer 0/1, NOT NULL, CheckConstraint, matching `meta_unavailable`'s own boolean convention), not merely rewritten to a new literal string. Reasoning: once the destination is `FILES_DIR/statements/<id>.parsed.json` — always, deterministically, for every id — a full path column stores nothing a marker doesn't already imply; the one property worth preserving (`StatementStore.all()`/`query()` skip a filesystem read entirely for the majority of statements that were never parsed, per `money_io._reinline_statement`'s own `if has_parsed_rows:` guard, rather than probing a file that provably doesn't exist) is served exactly as well by a boolean as by a path string. `attachments` gets NO equivalent column: its sidecar is unconditionally written in the SAME `create()` call as the metadata row, so "has this row's derived cache been written" is always true by construction there — a marker would be redundant, not merely lower-value; the pointer STAYS asymmetric across the two stores for a real reason (statements' cache arrives later, is rewritten repeatedly, and is nullable-and-meaningfully-so; attachments' cache is written once, atomically, with the row). `money_io._reinline_statement`/`_statement_row`/`import_statements`/`export_statements` all moved onto the new flag+deterministic-path shape; `portable_bridge._wipe_statements_meta`/`apply_money_bundle`'s live-set pruning derive each row's path from its own id instead of reading a stored column. `STATEMENTS_PARSED_DIR` is RETIRED from `core/paths.py`; `STATEMENTS_FILES_DIR` takes its slot in `INTENTIONALLY_FILE_BACKED` (it now holds `.parsed.json` files alongside raw originals). The whole `files/` tree's chmod hardening (previously only `STATEMENTS_PARSED_DIR` was 0700, an asymmetry with receipts'/attachments' equally-sensitive sidecars) is leveled up to `FILES_DIR` and all four of its leaf directories. Migration (`0046_derived_data_colocation.py`) mirrors 0045's own non-destructive, per-row-fault-tolerant, boot-time-fail-closed shape exactly: move + verify (sha256 AND JSON-equality) + set the flag + rename the old file `.migrated-<ts>` (statements), rename the old attachment payload `.migrated-<ts>` after copying (attachments), sweep genuine orphans (including stale `.import-tmp-<hex>` staged writes) to `.removed-<ts>` — never delete, always re-verify, one caught-and-counted failure per malformed row, one halting `_VerificationFailed` for a real post-write mismatch. Revision 0007 (the original from-scratch cutover) was edited in place a second time (the same precedent its own `money_as_text` amendment set for revision 0008) to carry a frozen, self-contained copy of the pre-0046 statement row builder/reader — it runs BEFORE 0046 in a from-scratch chain, so `statements_meta` still has ITS original schema at that point; the live `money_io` builders can no longer be reused there.

**Security review fix round 2 (2026-08-22, pre-merge — 9 findings, all closed).** (1) `_migrate_one_statement_row`'s `old_path` (the legacy `parsed_rows_path` source, read then renamed away) gets the same `_assert_contained` re-proof `new_path` already had — a `parsed_rows_path` string surviving a portable-bundle restore is exactly the untrusted-input class FR-C1 already exists to guard against; a violation lands in that row's `report["failed"]` entry, never a boot-halting raise. **`intel_signals` splits into `intel_stories` + `signal_timeline_entries` + `daily_digests` (revision `202608301500`, RFC `docs/rfc/intel-signals-data-model.md`, Phase 1 of a phased plan — foundational schema/migration/choke landed here; writer call sites, the identity fix's runtime half, the portable bridge, and the `asset_brief.news[]` live-query rewrite are explicitly LATER, separately-dispatched work).** The old `intel_signals` was a genuinely multi-writer table: 7 story-arc types (`asset`/`topic`/`risk`/`opportunity`/`macro`/`monitoring`/`price_alert`) sharing one shape, PLUS `daily_digest` rows that carried a structurally foreign shape (no `ticker`/`timeline`, a `daily-digest-<date>` id, always upserted never a list) — one table with a `summary` key meaning two different things at two different scopes (a story's running state vs. one timeline entry's own dated development) and an unbounded JSON `timeline` list nothing indexed into. Three tables now match the three real shapes. **`intel_stories`**: promoted query-surface columns (`type`/`instrument_id`/`ticker`/`label`/`status`/lifecycle flags) + a verbatim `payload` — the `accounts`/`evidence` shape, chosen because real per-type extra fields exist (e.g. `risk` rows carry `status_reason`, no equivalent on any other type) that promoting-everything would mean guessing past what's used. `summary` is renamed `current_summary` (collision-avoidance — the same name a timeline entry's OWN `summary` field now sits directly beside). **`signal_timeline_entries`**: a direct structural copy of `session_messages` (migration `202608241937`) with one deliberate difference — `session_messages` uses a bare DB-assigned `INTEGER PRIMARY KEY` because nothing outside it ever references a message's identity, but a timeline entry's `duplicate_of_id`/`contradicts`/`supersedes` (ADR `2026-08-28-sourced-and-corroborated-intel-signal-updates`) are stable string ids the model itself references across turns — so this table carries BOTH a DB-assigned `seq` (ordering, race-free) AND the pre-existing `uuid4().hex` `id` (business identity, UNIQUE-indexed). FK `signal_id -> intel_stories.id ON DELETE CASCADE`. **`daily_digests`**: `date` ('YYYY-MM-DD') is the LITERAL primary key, not a synthetic id — `_write_inapp_digest` already treated the date as the real key; a day both an EOD and a premarket digest fire, the later write overwrites the earlier one — this migration preserves that exact pre-existing behavior with an honest storage shape, not a silent fix. `summary` renamed `message` (same collision-avoidance reasoning). **Deliberate policy change, called out not silent**: `daily_digests` is WIPE-ONLY, NOT bridged (`portable_bridge.BRIDGED`'s `"intel_signals.json"` entry — and its `_WIPE_FNS` counterpart — were REMOVED outright, not migrated to the new tables: a delivered-digest record is regenerable notification history, not a book fact, and only ever rode inside `intel_signals.json` because it was never given its own file); **`claims` — cross-subject push-dedup registry (revision `202608301800`, owner override of RFC `intel-signals-data-model` §4's "NO-GO", ADR `2026-08-30-claims-registry-cross-subject-push-dedup`).** The RFC's own audit reasoned some of `intel_stories`' ticker fragmentation is legitimate (multiple price alerts on one ticker aren't duplicates) and recommended NOT building a cross-subject dedup table, citing ADR `2026-08-28-cross-subject-fan-out-and-asset-brief-consolidation`'s deliberately narrow same-tick-only pairing (`_find_linked_pairs`). The owner overrode that recommendation after a direct, evidenced incident: a ticker's topic-side and asset-side signals each independently pushed an external alert about the SAME real corporate development, ~10 hours apart — a cross-TICK duplicate `_find_linked_pairs` cannot catch by construction. `claims` (`id`/`group_key`/`statement`/`status` (`active`/`superseded`/`flagged`, reusing `signal_timeline_entries`' own vocabulary)/`duplicate_of_claim_id`/`contradicts_claim_id`/`sources[]` (server-built, never model-chosen)/`story_ids[]`/`materiality`/`decision_relevant`/`created_at`/`confirmed_at`/`pushed_at`/`payload`) is a single flat table, no FK to `intel_stories` (opaque `story_ids`, the same loose-coupling convention `instrument_id` already uses). `services.claims.group_key_for(story_type, instrument_ids)` is the identity function: only the news/development-tracking types (`asset`/`topic`/`risk`/`opportunity`/`macro`) ever resolve a key, and only when the caller-resolved instrument ids collapse to EXACTLY ONE — `price_alert`/`daily_digest`/`monitoring`, or a story spanning more than one instrument, NEVER get one, so the RFC's own price-alert-vs-topic conflation concern holds structurally, not by convention. `analyst._push_decision` gained one new gate (sixth, after the existing grounded gate): a `group_key` with an active claim pushed within `_CLAIM_PUSH_FRESHNESS_HOURS` (24h — deliberately NOT `_STALE_PUSH_HOURS`'s 6h, a different question that would miss the ~10h-apart proven incident) suppresses the push as `"duplicate_claim"`; `services.claims.apply_claim_push` records/refreshes the claim right beside the existing `_push_analysis` call at both push-decision call sites (`_process_row`, `_process_linked_pair` — the latter resolves ONE group_key for both sides, since a linked pair is by construction about the same instrument). `ClaimsStore.record_push` does its own atomic read-then-decide under the table's own lock (mirrors `IntelStoriesStore.upsert`), so no `locked_unit_of_work` composition is needed — it never touches more than the one table. NOT bridged/portable and NOT added to any wipe set in this change (out of scope — the registry is new enough that export/reset behavior is a deliberately deferred follow-up, not a silent omission).

**`owned_assets` + `owned_asset_categories` — the Assets tab domain (revision `202609061000_owned_assets`, ADR `2026-09-06-assets-tab-faithful-port`).** A brand-new domain for things you own that are valued by a dated manual mark, not a ledger balance or a price feed — property, vehicles, watches & jewellery, art, precious metals, cash-value policies, and user-created categories. Both tables are plain `book_payload_table("<name>")` — the identical Tier-1 `(book_id, seq, id PK, payload)` shape planning already uses, one unique `ix_<name>_book_seq` index each, the only FK `book_id -> books.id`. **No cross-table FK**: an asset's `category` (a builtin key or a custom category's `key`) and `loan_account_id` (a liability account) are opaque references resolved by `services/owned_assets.py`, matching every other Tier-1 store's loose-coupling convention — `backend/db/owned_assets_store.py` (`OwnedAssetsStore`/`OwnedAssetCategoriesStore`) does not itself know the category set or reach into `AccountStore`. **Builtin categories are a service-level module constant** (`services.owned_assets.CATEGORIES` — property/vehicle/watch/art/metal/policy/other), never stored; only a user-created category lives in `owned_asset_categories` (`key` `c_<slug>_<4 base36>`, minted idempotently on a case-insensitive label match — checked against the WHOLE set, builtins included, so re-adding "Property" returns the builtin instead of shadowing it). `services.owned_assets.categories()` merges the two, inserting customs before "Other" so it stays the last picker choice. **Value is the newest mark, never a stored field**: `marks[]` is an ordered child collection (the `commitments.installments[]` shape) sorted newest-first by `(date, created_at)`; a new mark is always PREPENDED (well, re-sorted in) by `OwnedAssetsStore.add_mark`, never overwritten — `update_asset`'s edit whitelist explicitly excludes `marks` and every disposal field, so an identity edit (rename, re-category, cost correction) can never touch the value history. Stored `marks[]` hold VALUATIONS only (`{id, date, value, note, by, created_at, edited_at}`); the purchase point is DERIVED on read from `(category, cost, cost_date)` by `services.owned_assets_valuation.series()` and projected as `{id: "purchase", kind: "purchase"}` (none for `policy`, none without a date) — create writes exactly one valuation and no system facts (ADR `2026-09-26-owned-asset-purchase-point-is-derived`; migration `202609261500_owned_asset_purchase_point_derived` dropped the old stored "entered on add" copies, normalized `source`/`"— none"` notes, stripped the system "Added" fact and released loans held by sold assets). Projection-only fields: `value`, `valued_on`, `share_value` (native currency), `marks[].kind`. Insurance and maturity are typed identity fields (`insured: bool`, `maturity_date: YYYY-MM-DD | null`); review cadence and linked asset-review Automations are retired. **The ONE write choke** is `services.owned_assets.apply_owned_asset_change(change)` (ops: `create | update | add_mark | correct_mark | remove_mark | dispose | delete | set_photo | add_doc | update_doc | remove_doc | create_category`); `dispose` composes the disposal's ledger transaction and the asset's archive into ONE `db.engine.locked_unit_of_work(owned_assets, transactions, txn_audit)` transaction, posting a single-leg `kind="investment"` inflow via `ledger_service.create_transaction(..., conn=conn)` with `external_refs=[{"source":"asset_disposal","ref":<asset_id>}]` — the SAME `create_transaction` idempotency guard every other choke relies on makes a retried dispose a safe no-op rather than a doubled deposit. `delete` is a genuine hard delete ("Delete asset", for things that should never have existed); disposal keeps history (`archived`/`disposed_on`/`disposal_proceeds`/`disposal_txn_id`/`disposal_account_id`) instead. **The net-worth seam** is `services/owned_assets_valuation.py` — deliberately narrow imports (the store + `core.fx` + stdlib only, no `services.ledger`) so the ledger layer can import IT without a cycle: `value_as_of(asset, as_of)` (the newest mark on/before `as_of`, or the newest of all when `as_of` is None — an asset's marks ARE its price series, so a historical query is answered the same honest way as today's), `band_of(category)` (`property`→`"property"`, `metal`→`"commodity"`, everything else→`"other_asset"`), and `values_by_band(base, *, as_of=None, rates=None)` (share-adjusted `value × share_pct/100`, base-converted, excluding an `archived` row when `as_of` is None or a row already `disposed_on` on/before a historical `as_of`). **Wired into net worth (the follow-on lane, same ADR):** `ledger.net_worth()` folds `values_by_band(base, rates=rates)` into `account_classes[band]` (so `account_classes`, `accounts_asset` and `net_worth` move together) and additionally reports `breakdown.owned_assets` as their Σ; `ledger._breakdown_as_of` takes a `manual_assets_base` band map (the same `option_mark_base` precedent) so `net_worth_bands()` (today) and `net_worth_history()` (PER POINT, `as_of=<that point's date>` — a point before an asset's first mark contributes 0, a point on/after `disposed_on` contributes 0, otherwise the newest mark on/before that date) both value manually-marked assets honestly rather than back-projecting today's mark. `portfolio_rows.projected_rows()` gains `_asset_as_row` (illiquid, banded by `band_of(category)`, `quantity` = the share-adjusted base value with `price=1` so `base_value == quantity`, `cost_basis` derived so the shared `_project` fold reconciles to the honest share-adjusted cost) so allocation/reach/KPIs/gains pick assets up for free. Photos/docs are attachment references only (`photo_ref`, `docs[] {ref_id, name, added_on, lucius_readable}`), persisted via the existing `services.attachment_ingress.persist_inbound_file` and served by the existing `/api/uploads/{ref}/image|file` — no new blob storage. **Portability**: `assets.json`/`asset_categories.json` join `PORTABLE_FILES`, `db.portable_bridge.BRIDGED` through normalization-aware bridges that strip retired review fields and prevent legacy asset-review Automations from returning and the `/api/reset` wipe map. **Lucius tools** (`ai/tools/assets.py`; the three value tools in `ai/tools/asset_values.py`): `list_assets`/`get_asset` (read), `create_asset`/`update_asset` (identity only, never `value`)/`record_asset_value`/`correct_asset_value`/`remove_asset_value`/`dispose_asset`/`delete_asset`/`create_asset_category`, all `mutates=("assets",)` (`dispose_asset` additionally `"ledger"` — it posts a real transaction). **Mentions**: an `asset` `EntityDescriptor` (`services/mentions/descriptors/new_types.py`) over the service's `list_assets()` projection — name/category/value/valued_on/share_pct/notes only, never `marks`/`docs`/`facts`.

**Owned-assets review-removal migration (`202609101600_remove_owned_asset_reviews`).** Migration and old-bundle import extract legacy Insured/Matures facts into typed fields, strip retired review metadata, and remove only legacy asset-review schedules. The normalization-aware `assets.json`, `asset_categories.json`, and `automations.json` import bridges prevent that retired state from returning; malformed or non-finite asset data fails the import rather than poisoning net-worth calculations.
