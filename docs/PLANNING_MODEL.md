# Planning model — envelopes, commitments, credit cards, spend rules

> **On-demand reference.** Not loaded into every turn — read it when you touch this area.
> Decisions and their reasoning live in [`docs/adr/`](adr/); this file states current truth.

**Planning (YNAB):** `available(m,cat) = max(0, avail(m−1)) + assigned + activity` — activity is SIGNED in-month (an overspend counts negative); only the CARRY into next month clamps at 0, so a still-negative envelope resets and its hole is charged to next month's Ready to Assign (ADR `2026-09-09-ready-to-assign-follows-ynab-envelopes-are-the-category`, restoring ADR `2026-07-02-balance-based-rta`, superseding `2026-09-08-ready-to-assign-is-unassigned-cash` one day after it shipped); `ready_to_assign = cash_as_of + card_credit − pre_budget_baseline − held_in_envelopes − held_outside_envelopes − card_spend_not_covered` (`card_credit` = every card's balance above zero, ADR `2026-11-02-a-card-in-credit-is-budget-money`: a card in credit is budget money, a spend on it pays from the credit first and only the rest is coverable debt, and a refund drains the payment envelope only by the debt it shrinks), where `held_in_envelopes` is the SIGNED Σ available (can be negative — an overspent envelope does not move RTA: for a CASH overspend cash already dropped by the same amount, and for a CARD overspend cash never moved at all, so `card_spend_not_covered` cancels the row's drain instead) and `card_spend_not_covered` is this month's uncovered card-spend activity on a LINKED envelope, RTA-neutral, never a standing debt total. **`held_outside_envelopes`** (ADR `2026-09-10-uncategorized-and-unlinked-cash-spend-holds-until-month-end`, amending 2026-09-09's drain-immediately "one fix" after direct YNAB observation) is the no-bucket term: CASH spend that no envelope saw — uncategorized ("Uncategorized") or on a category linked to none — HOLDS its own hole under the SAME clamped carry, `held(m) = min(0, max(0, held(m−1)) + cash_activity(m))`, one instance for Uncategorized and one PER unlinked category (never one over their sum, or one category's refund would cancel another's still-open hole). It is `_available`'s recurrence with `assigned ≡ 0` — nothing can be assigned to a bucket that is not an envelope — plus ONE asymmetry: the upper `min(0, …)` clamp, so a no-bucket bucket holds HOLES but never a SURPLUS (an inflow under an unlinked label is unassigned cash and still raises RTA, matching the rule income landing on an unlinked category already follows). With the value pinned ≤ 0 the prior carry is provably 0, so the recursion collapses to the month's own activity and takes no walk. RTA does not move at the spend; the hole resets at the roll and is charged to next month exactly once; labelling the transaction, or linking its category to an envelope, before then makes the hold evaporate. CASH-ONLY, structurally: it reads `_cash_activity_map` — filled by the SAME pass as `_activity_map`, but ONLY from legs whose MOVING account is in `ctx["cash_ids"]`, the exact set `_cash_as_of` sums, so both sides of the identity provably draw from one account universe, and valued the way that side values it — the moving leg's OWN native amount at the CURRENT rates, never a transfer's stamped `base_amount` (which `_transfer_base_value` takes from whichever leg was already in base currency, so routinely the OTHER leg at the bank's rate) and never a stamp whose `base_currency` no longer matches the base. The coverage cap's pool mirrors ENVELOPE math (stamped, rate-locked); the hold's mirrors CASH math — ADR correction 3. NO spend on a `credit` account feeds it (a card had no cash to lose; its shortfall stays on the card and surfaces via the payment row's `underfunded`/`owed`) — not merely a payment-TRACKED one. Deliberately NOT the accumulator `_capped_card_credits` resolves its headroom against: that one admits every plan-source leg except a payment-tracked card's own spend, so it includes an archived card, one just retyped to `credit`, and a card's own outgoing categorized transfer. Sharing the two fabricated Ready to Assign — see the correction in ADR `2026-09-10-uncategorized-and-unlinked-cash-spend-holds-until-month-end`. `RTA ≤ cash − baseline` is retired; the identity instead closes exactly: `RTA + held_in_envelopes + held_outside_envelopes + card_spend_not_covered + baseline == cash_as_of`. The wire keeps `held_in_envelopes` and `held_outside_envelopes` as SEPARATE terms — the former stays exactly the Σ over envelope rows that `totals.available` renders, so the header can never disagree with the identity beside it. Computed-not-stored. "Others" group is default catch-all, cannot be deleted. **Envelope ⊥ category — the full split** (`.claude/rfcs/envelope-category-full-split.md`, supersedes `envelope-not-category.md`'s "category-first birth"): envelope and category creation are FULLY INDEPENDENT — `envelopes.create_envelope(name, group_id?)` mints NO category (a zero-category envelope is legal — a named pot with a target); `categories.create_category` mints NO envelope (the auto-mint hook is REMOVED). A category is a pure transaction label (Manage Categories); a **link** (`envelope.category_keys`, ≤1 envelope per category) is what makes it budgetable. **Row identity = envelope id**: `budget_month()` renders ONE ROW PER NON-ARCHIVED ENVELOPE, full stop — the pseudo-row family (a no-envelope category rendering its own row) is GONE, so an unlinked category has NO budget row. A row's `key` is `category_keys[0]` for a 1:1/merged row (byte-identical to the pre-split table) or the envelope's OWN id for a zero-category row (`assign`/`set_target` accept either form — `services.planning.row_key`/`_resolve_envelope` resolve a category-or-envelope-id ref to the row). Assigned amounts AND targets are both stored keyed by ENVELOPE id (`_budget_key`/`_assigned_amt`/`_set_assigned_amt` and the parallel `_target_for`/`_set_target_for` facades resolve ANY category to its envelope's ONE slot, with a category-keyed-remnant read fallback), so a 1:1 book is byte-identical to the pre-split table (pinned: `tests/test_envelope_migration.py::test_full_split_migration_is_byte_identical_for_all_1to1_book`). A merged (N>1) envelope's member categories fold into one row — assigned is read ONCE via the facade (summing per member double-counts — the "double-count trap"), activity is a genuine sum across members (`_row_activity`, shared with `_available`/auto-assign). **Groups are envelope-keyed**: `envelope.group_id`/`order` is the ONLY placement authority `budget_month` reads (`_envelope_group_buckets`/`_grouped_rows` — lazily `ensure_others()` since no pseudo-row triggers it anymore); Groups are ENVELOPE groups — the `envelope_groups` table (renamed from `category_groups`; ADR `2026-10-03-category-group-membership-is-retired`) holds only `{id, name, collapsed, order, is_others}`; there is NO category→group membership anywhere (`categories` belongs to no group, `create_category` can never create one, a group is created only by `group_create`, and a name that is a synced group's or a `__x__` sentinel is refused). INCOME categories are flat: `income_view()` returns one `categories` list, and the money-flow graph links them straight to the total (always four columns; compact three). `move_category` resolves a linked-category-or-envelope-id ref via `_resolve_envelope` (REFUSES an income category — it has no envelope and no group; REFUSES a non-primary N>1 member — split it out first; a genuinely unlinked category — link it via `envelope_add_category` first; or a Commitments-synced envelope — same `is_commitments_synced` guard merge/split/delete already enforce, EXTRA A 2026-07-04: a Lucius reorg once escaped commitment envelopes from the pinned Commitments group through this one un-guarded path; `sync_commitment_envelopes` also self-heals an already-drifted book's group placement on its next run) and `reorder_categories` resolves each requested key to its envelope, renumbering `envelope.order` to match. `set_target`/`write_category_note` resolve to the row's PRIMARY key (`services.planning.row_key`) so a write via a non-primary member never lands a ghost the row can't read. **Unbudgeted surface**: a LABELED-but-unlinked category's activity renders in a synthetic `__unbudgeted__` display group (`unbudgeted: true`, same family as the blank-category `__unsorted__`/`unsorted: true` row) and HOLDS its own hole there until the month-end roll rather than reducing Ready to Assign on the spot (ADR `2026-09-10-uncategorized-and-unlinked-cash-spend-holds-until-month-end`, amending 2026-09-09: the Unbudgeted/Uncategorized distinction still does not change RTA treatment — one rule for "no bucket" — but that one rule is now HOLD, not drain, and it is a CASH-ONLY rule: the same spend on ANY `credit` account is RTA-neutral like every other card spend, since no cash moved). `budget_month`'s wire `totals.activity`/`totals.available` are a PLAIN Σ over the ENVELOPE ROWS — neither derived group is folded in (ADR `2026-09-08-ready-to-assign-is-unassigned-cash`, superseding the BE-TOTALS-UNBUDGETED-CONTRACT fold of 2026-07-04: neither group holds anything, so folding them made "Total available" disagree with the `held_in_envelopes` printed beside it — the identity's own term is exactly that same Σ; both still RENDER as display groups); `_ready_to_assign`'s own computation (`on_budget_cash − baseline − Σ available (SIGNED) − card_spend_not_covered`) never folds Unbudgeted or Uncategorized as line items at all — both are already inside `on_budget_cash`'s drop, per the identity above. Money-mutating rules: `auto_assign_preview`/`move_money` are envelope-row-aware — ONE `apply_budget_change` step per row (never per member), and `move_money` REFUSES two categories that resolve to the same envelope slot. `rename_category`'s envelope hook (`on_category_renamed`) folds BOTH sides' legacy category-keyed remnants into the surviving slot on every branch and, merging a member of an N>1 envelope, only detaches that one category (split semantics). `sync_commitment_envelopes` mints/retires a ZERO-CATEGORY envelope directly per active commitment (via `envelopes.create_envelope`) — since the category-opaque-ids migration retired the `commitment_{id}` bot-managed category, `envelopes.on_category_created` (its one caller) no longer exists. Six envelope-lifecycle `apply_budget_change` types (delegate to `services.envelopes`): `envelope_create` (RFC §Backend 1, REST `POST /api/planning/envelopes`, accepts optional `color`), `envelope_add_category` (links an UNLINKED category — not composable from split+merge, no source envelope exists; REFUSES 409 if already linked, REST `POST /api/planning/envelopes/{id}/add-category`), `envelope_merge`, `envelope_split_category`, `envelope_rename`, `envelope_delete` (hard-deletes with a server-held Undo token — `envelope_restore` is RETIRED, ADR `2026-09-26-deleting-an-envelope-deletes-it`). REST: `GET /api/planning/envelopes` (`?include_archived`), `GET /api/planning/envelopes/archived` (historical only — nothing new archives), `POST /api/planning/envelopes`, `POST /api/planning/envelopes/merge`, `POST /api/planning/envelopes/{id}/split`, `POST /api/planning/envelopes/{id}/add-category`, `PATCH /api/planning/envelopes/{id}` (`{name?, color?}`), `GET /api/planning/envelopes/{id}/delete-preview?ym=` (the realized-Ready-to-Assign-change figure, computed never written — `{month, envelope_id, available, delta_rta}`, see `planning.envelope_delete_preview`/`_envelope_delete_delta`; the confirm dialog's own number, a LOWER BOUND rather than always exact when the envelope's members carry live payment-tracked card spend this envelope's headroom was covering — unlinking drops that coverage, freeing MORE room on the card's own payment envelope than this envelope-local figure prices in, never less), `DELETE /api/planning/envelopes/{id}?ym=` (returns `{ok, undo_token, former_category_ids, zeroed_assignments, month, available, delta_rta}` — the latter three are the SAME preview figure, realized an instant before the write), `POST /api/planning/envelopes/undo-delete` (`{token}`, 204). **Handoff-port deltas (2026-07-04, `.claude/rfcs/budget-envelopes-handoff-port.md`):** `split_category` UNLINKS ONLY — the category becomes envelope-less (→ the `__unbudgeted__` surface), NO 1:1 envelope is minted, and a SOLE member may be split (the envelope stays, possibly zero-category, keeping its pool); `envelope_delete` detaches all members, zeroes env-keyed assignments across ALL months (a POSITIVE balance releases to Ready to Assign; a NEGATIVE balance is neither forgiven NOR charged now — the detached members become UNLINKED categories, and since ADR `2026-09-10-uncategorized-and-unlinked-cash-spend-holds-until-month-end` an unlinked category's CASH spend holds the same hole in `held_outside_envelopes` under the same clamped carry, so the hold changes hands rather than dying with the row and the charge still waits for the roll. The move is `available(m, E) − Σ_c min(0, cash_activity(m, c))` = `max(0, prev_carry) + assigned + Σ_c max(0, cash_c) + Σ_c non_cash_c` — NOT `max(0, cash_activity)` over the envelope's summed activity, since a MERGED envelope's members hold SEPARATELY once detached (spend 100 on one member + refund 100 on another moves RTA +100 where the summed form says 0). The first three terms are ≥ 0, so deleting RAISES Ready to Assign or leaves it flat on every book free of ONE shape: `Σ_c non_cash_c` goes negative when a `credit`-account leg drains a LINKED envelope with nothing to offset it (an archived card's spend, a card-funded categorized transfer or investment buy — all escaping the payment-envelope fold), which is a logged, deferred pre-existing bug that INFLATES RTA before the delete rather than a fault in the delete. Held as a property over random books, with that exception pinned beside it, in `tests/test_delete_envelope_never_lowers_rta.py`), clears target/note/50-30-20-cap and HARD-DELETES the row (owner decision 2026-09-26, "we should stop archiving envelope, just delete" — superseding the archive-with-metadata shape; ADR `2026-09-26-deleting-an-envelope-deletes-it`); the before-image (row + target/note/cap/assignments) is snapshotted server-side under a one-shot token in the SAME transaction (`PlanStateStore.set_envelope_delete_undo`, `plan_state.payload["budget"]["envelope_delete_undo"]` — `fresh_start_undo`'s exact pattern), and `services.envelopes.undo_delete_envelope(token)` replays it exactly (same id; re-links former members still unlinked, group kept if alive else Others) and consumes the token — a stale/unknown token is a `ConflictError` (409). Every other envelope death (merge's source, a category rekey's sole-member merge, a category-delete's now-emptied envelope, a dropped-out Commitment's or credit card's synced envelope) hard-deletes the same way, clearing that envelope's own target/note/cap with it — none of those get a token, only the user-facing `envelope_delete` does. `restore_envelope`/`list_archived_envelopes` (the Lucius tools) and the `envelope_restore` op/REST route are RETIRED with the archive model — a delete just made is undone by the UI's own short-lived Undo pill, an older Lucius write by `restore_checkpoint`; envelopes archived BEFORE this change keep reading fine (`GET /api/planning/envelopes/archived`), permanently frozen, since nothing archives going forward; envelopes own a display `color` (`""` = derive from first member category); `move_money` accepts the `__rta` sentinel on exactly ONE end (to `__rta` = release, capped by the source row's AVAILABLE this month — not this-month assigned, FEB-02 fix 2026-07-04, ADR `2026-07-04-move-money-caps-at-available-not-assigned.md`: carried-over money is movable, so assigned may go NEGATIVE, absorbed by the same `max(0, prev)+assigned+activity` identity an in-month overspend already uses (the clamp is on the CARRY only — ADR `2026-09-09-ready-to-assign-follows-ynab-envelopes-are-the-category`); from `__rta` = fund, no cap — RTA may go negative like assign); target specs gain preset due fields `due_weekday` (0–6, weekly — weekly `needed_this_month` = amount × occurrences of that weekday), `due_day` (1–28 | −1 = last, monthly, display-only) and `date` on yearly (display-only) — presets, NOT RRULE (ADR `2026-07-04-target-deadline-presets-not-rrule.md`). **Target flavor** (`needs_whole_amount`, ADR `2026-07-10-set-aside-by-date-target-flavor.md`): a target measures progress one of four ways — **Set aside** (recurring, `True`) → this-month **assigned** (funded stays funded after you spend); **Fill up to** (recurring, `False`) → **funded-this-month** = rollover + assigned = `available − activity` (spending doesn't re-open it mid-month — it refills next month, NOT `available_now` after spending); **Set aside by [date]** (`by_date`, `True`) → **cumulative contributions** `assigned_to_date` (spending never sets the dated goal back — `BudgetAssignmentsStore.all_map()` folds every month ≤ current); **Have a balance of** (`by_date`, `False`, the by_date default) → running **available** (a savings pot; spending sets you back). Default `needs_whole_amount=True` for EVERY type (one clean rule, no per-type/legacy branching); `by_date` persists `True` explicitly since its read-back default is `False`. The client (`planData.statusOf`) mirrors this and `useBudgetModel.recompute` TRUSTS the server status for `by_date` rows (never re-derives). Category deletion lives in the shared 4-kind Manage-categories modal (frontend) → `DELETE /api/categories/{key}?reassign_to=` (omitting reassign is the explicit "leave → Uncategorized" choice); the income-only InflowManager is retired. **Migration** (idempotent, non-fatal, boot-ordered in `main.py`): `ensure_envelopes_migrated` (first-boot: mints 1:1 envelopes for every budgeted category, re-keys assignments) → `resync_legacy_category_keyed_assignments` → `resync_orphaned_budgeted_categories` (mints an envelope for any category STILL carrying a raw assignment/target under its bare key — grandfathers the pre-split pseudo-row family without ever auto-minting for a bare, dataless category) → `stamp_missing_envelope_placement` (derives `group_id`/`order` for any envelope missing them, else Others) → `resync_legacy_category_keyed_targets` (mirrors the assignments resync for targets). RFC: `.claude/rfcs/envelope-not-category.md` + `.claude/rfcs/envelope-category-full-split.md`; UI spec: `.claude/rfcs/envelope-p4-ui-spec.md`. **Categorized transfers (owner decision 2026-07-03):** a `kind=transfer` row may carry an optional category — `_activity_by_category` folds it by an XOR rule on which leg is on-budget: exactly ONE on-budget leg → the category absorbs that leg's own amount (from-leg on-budget → drains the envelope like an expense, e.g. a loan payment leaving to an off-budget lender; to-leg on-budget → credits it like an income refund); BOTH legs on-budget → folds nothing (the cash nets to zero on its own — the label is inert); an UNCATEGORIZED transfer is unchanged (drains/credits RTA directly via cash, no envelope). A categorized transfer to an unlinked category falls into the same synthetic `__unbudgeted__` group as any other labeled-but-unlinked spending. RFC/ADR: `docs/adr/2026-07-03-categorized-transfers.md`.

**The RTA breakdown popover's flow framing (ADR `2026-09-13-rta-popover-flow-framing`)** presents
the SAME stock identity above as YNAB's own flow terms, purely for display — an exact algebraic
rearrangement, never a second independently-computed running total: `RTA(m) = carried_in +
inflow − assigned(m) − cash_overspending_prev − assigned_in_future(m)`, where `carried_in =
_ready_to_assign(ctx, prev)` (last month's RTA before its OWN future-assigned clamp), `inflow(m)
= Δcash(m) − totals.activity(m) − held_outside_envelopes(m) − card_spend_not_covered(m)` (net
cash movement no bucket absorbed — computed from its OWN four inputs, NEVER back-solved from
`rta − everything_else`, which would make every check built on it vacuous), and
`cash_overspending(m) = Σ_rows max(0, −available(m, row)) − card_spend_not_covered(m) −
held_outside_envelopes(m)` — provably ≥ 0 on every book (the card term cancels exactly against
`_capped_card_credits`'s own per-row `Ov − u = max(0, −headroom)` identity), which is why it is
genuinely labelled "Cash" Overspending and a card's debt is never charged to RTA at the roll.
Two new additive `budget_month` wire keys carry this: `flow` (`{prev_month, carried_in, inflow,
cash_overspending_prev}`, `None` at and below the floor — `_available` starts the carry at 0
there, so there is no real predecessor month to read) and `cash_overspending` (this month's own
open figure, always present, even at the floor). Both are computed from state `_build_context`
already resolves for months `m` and `m−1` — no new store, no new fold over the ledger. Two
previous-month lines render SEPARATELY in the popover ("Ready to Assign Left Over from
{PrevMonth}" / "Cash Overspending in {PrevMonth}") rather than folded, reversing the retired
2026-07 popover spec's fold (`.claude/rfcs/rta-breakdown-popover-spec.md` §11) — under THIS
identity the charge lands for the first and only time on the receiving month's own screen, so
folding it away would delete the one place the hold/reset mechanic can show its work. The
desktop rail (`budgetRail.tsx`) and the fresh-start dialog keep the STOCK framing unchanged —
the rail answers "where is the money now," the popover "how did I get this number," and a fresh
start's hypothetical month has no predecessor by construction. Wording is YNAB's own literal
phrasing with the real month name interpolated (owner: "I want everything to match YNAB. So
don't make any deviation.") — the one exception is "Assigned in future months," which stays
generic since it is a clamped aggregate over potentially several later months and naming one
would be a false claim, not merely an imperfect one. Property-tested via
`tests/test_rta_flow_terms_property.py`, mirroring `test_rta_identity_property.py`'s
differential-fuzz technique with two non-circular oracles (a second `_build_context` for
`carried_in`, a raw-transaction Δcash walk for `inflow`).

**Carry floor / "start fresh" (ADR `2026-09-08-budget-fresh-start-moves-the-floor-not-the-data`)** — `budget_config.rollover_start` (profile) is the floor of BOTH recursive walks: `_available` stops carrying at it (`month <= ctx["floor"]` → `prev_carry = 0`) and `_ready_to_assign` returns 0 strictly before it. `_floor_month(txns, floor_override=None)` resolves it (`rollover_start` → first data month → this month) and `_build_context(month, floor_override=None)` threads it; `budget_month` echoes the STORED value read-only as `rollover_start` (distinct from `ctx["floor"]`, which falls back). **`planning.fresh_start_preview(month)`** answers "what would RTA be if the carry stopped here" by building a SECOND context with `floor_override=month` and reading the same `_display_rta` — it writes NOTHING; a write-then-revert preview is explicitly rejected (it makes the book wrong for every concurrent reader and checkpoints a phantom edit). The SERVICE returns `{month, ready_to_assign_after, cash_now, held_in_envelopes, card_spend_not_covered, baseline}` plus `assigned_in_future` only when a later month carries assignments — exactly the RTA identity on the post-clear context, so `ready_to_assign_after == round(cash_now − baseline − held_in_envelopes − card_spend_not_covered − assigned_in_future, 2)` with no residual term. Both subtracted terms are SIGNED: with the month's assignments zeroed each envelope row reduces to its OWN month's activity, so `held_in_envelopes` is NEGATIVE on any book with a budgeted spend in the cleared month, POSITIVE for a same-month refund or covered card swipe (ADR `2026-09-09-ready-to-assign-follows-ynab-envelopes-are-the-category`; the collapse of the old seven-key shape survives unchanged from ADR `2026-09-08-ready-to-assign-is-unassigned-cash` — `ready_to_assign_now`, `cash_at_month_start`, `carried_in_dropped`, `assigned_cleared`, `inflows`, `outside_envelopes_spend`, `other_movements` are all GONE, since every outflow was already inside `cash_now`'s own drop). `set_aside` is normally 0 after the clear; it survives only for a same-month refund into an envelope or a covered card credit, which is why the term exists rather than a "happens to hold" three-term ledger. The ROUTE projects exactly those keys.

**A fresh start is a BLANK SLATE for the month, not only a moved floor** (owner decision 2026-09-08, amending the ADR): `planning.fresh_start(month)` snapshots the month's assignments + the current floor, zeroes every assignment THROUGH `apply_budget_change`'s `assign` op, and moves the floor — one `locked_unit_of_work(budget_assignments, plan_state, profile)`, so half-applied is impossible. **The before-image never leaves the server**: the snapshot is taken INSIDE that transaction (so a concurrent assign can't be zeroed-but-unsnapshotted) and stored under a one-shot token at `plan_state.payload["budget"]["fresh_start_undo"]` via `PlanStateStore.set_fresh_start_undo` — the same singleton row + locked read-modify-write `set_home_engine_id` uses, so it survives a restart mid-undo-window. `fresh_start` returns `{token, month}` ONLY; `planning.undo_fresh_start(token)` loads that snapshot, replays it (byte-identical assignment table), and deletes it in the same transaction — a second undo, or a token that isn't the pending one, raises `ConflictError`. REST: `POST /api/planning/fresh-start` → `{token, month}`, `POST /api/planning/fresh-start/undo` `{token}` → 204. **"Resume earlier history" is the floor ONLY** — `PUT /api/planning/budget-config`, restoring no assignments, and its copy says so. Scope is the ZERO-BASED lens' assignment table only — never the proportional engine's config. `apply_budget_change` gained two keyword-only params for this: `conn=` (composes the `assign` op into the caller's transaction; RAISES if passed with any other op) and `allow_negative=` (a snapshot may hold a negative assigned amount — `move_money` out of a row produces one). **The safety property is the VALUES, not the kwarg's un-nameability**: pre-merge review found the first cut replayed a client-supplied assignment map with `allow_negative` set, reaching the same effect without naming it (a forged `{env: -5000}` in a future month moved displayed RTA via `_display_rta`'s clamp). The only amounts that path can now replay are ones the server itself wrote. An edit made between the fresh start and Undo is discarded by Undo (7s window; accepted).

**The dialog's LEDGER** (mechanics from 2026-09-08, terms restored by ADR `2026-09-09-ready-to-assign-follows-ynab-envelopes-are-the-category`, `held_outside_envelopes` added by ADR `2026-09-10-uncategorized-and-unlinked-cash-spend-holds-until-month-end`): `after = cash_now − baseline − held_in_envelopes − held_outside_envelopes − card_spend_not_covered (− assigned_in_future)`, exactly, on every book — `cash_now` is `cash_as_of` at the write, `held_in_envelopes` the SIGNED Σ available (can be negative — a still-open overspend the fresh start doesn't erase, since clearing assignments zeroes `assigned`, not this month's `activity`), `held_outside_envelopes` the same cash-only no-bucket hold the month payload carries (untouched by the clear — a fresh start zeroes assignments, not uncategorized/unlinked cash activity), and `card_spend_not_covered` the same uncovered-card-spend term the month payload carries, all computed on the cleared context. There is deliberately NO assigned term — the write clears the month's assignments, so at the new floor every envelope's available is just its own activity. The identity still closes exactly with no residual term: `outside_envelopes_spend` and `other_movements` stay RETIRED — a category with no envelope, an off-budget transfer, and a card payment are still not separate ledger terms, they are already inside `cash_now`'s own drop, same as before restoring the formula. Exact row labels and any hide-at-zero treatment for `held_in_envelopes` (now signed, not floor-clamped to ≥0 like the retired `set_aside`) are for the fresh-start ledger's rebuild to settle against the real dialog implementation; described here only at the formula level. The write is `planning.set_rollover_start(ym|None)` over `budgets.write_budget_config`, which stays the SINGLE writer of the field (shared with the `set_spending_limit_rollover_start` AI tool); it is deliberately NOT an `apply_budget_change` op (no money moves, and the field lives in the profile store, not the envelope/assignment tables that choke composes). **The anchor is validated in that writer** (`budgets._validate_anchor_month`), NOT at each caller: the AI tool writes there directly, and its own hand-rolled check used to accept `2026-99` and any future month while REST refused both — one writer, one rule (REST 422s; the tool wraps the same `ValidationError` into its `{ok:false,error}` shape). A malformed, impossible or FUTURE `rollover_start`/`budget_start` is refused; clearing (`None`/`""`) always succeeds. Why future is refused: the floor is also `_ready_to_assign`'s zero-line, so a floor ahead of today blanks every month the user can reach; a floor BEFORE the first data month stays legal (that is just "carry everything"). **The floor is ALSO the month-nav bound** (`_nav`: `earliest`/`can_go_back`), so starting fresh stops the Budget paging back past that month — kept (the bound and the carry are one fact) but DISCLOSED in the confirm dialog, and reversed by Resume. REST: `GET`/`PUT /api/planning/budget-config` (only `rollover_start` is settable — `pre_budget_baseline` is a cutover capture) and `GET /api/planning/fresh-start-preview?ym=`. UI: the "…" on the Budget tab row beside the lens switcher (`.pl-mast-tools`) → "Start fresh from ‹month›…" (`frontend/src/components/tabs/plan/useFreshStart.tsx`; on a phone it folds into the page header's overflow menu), a muted `.pl-sum-fresh` state line under the RTA hero, and a 7s Undo pill whose inverse is the same PUT with the previous value.

**Commitments** (the `commitments` table, `CommitmentsStore`/`services/commitments.py`) — a generic dated obligation (`kind` purchase|loan_repayment|auto_pay|goal) with `installments[]` (each `paid_txn_id`-linkable to a real ledger txn — ledger-anchored "paid", not a bare status flag), an optional `funding_plan[]` (the funding engine's coverage verdict, earmark reconciliation, projection events), and `envelope_id` (the Planning envelope synced to its next installment — a real foreign key, category-opaque-ids migration decision #4; the Plan budget row carries a ↗ chip that resolves this FK to deep-link the commitment via the refresh-safe `/commitments?open=<id>` route). `planning.sync_commitment_envelopes()` (renamed from `sync_commitment_categories`; REST path `/api/planning/sync-commitment-categories` unchanged) mints/reuses a ZERO-CATEGORY envelope (kind=expense pot, in the pinned "Commitments" group) for every active commitment with an unpaid installment and stamps its id onto `commitment.envelope_id` — NO category is minted at all anymore (the old `commitment_{id}` bot-managed category convention is retired; `envelopes.is_commitments_synced(envelope)` now checks `any commitment.envelope_id == envelope["id"]` instead of a category-key prefix scan). A commitment that drops out (paid off/cancelled/no unpaid installments) has its envelope retired (`envelopes.force_delete_commitment_envelope` — zeroed + hard-deleted, the one deliberate bypass of `delete_envelope`'s synced-guard since the sync job IS the bot) and its FK cleared. **Envelope drain (Mission #3):** `_activity_by_category` folds a CATEGORIZED `kind=investment` leg exactly like a budgeted expense/income refund — a buy (`from_account_id`) drains its envelope, a sell (`to_account_id`) credits it — so a synced Commitment DCA buy is RTA-neutral (the envelope absorbs the cash drop) instead of leaking Ready-to-Assign; an UNCATEGORIZED investment leg is excluded entirely (not even the Uncategorized bucket) and still moves RTA directly via cash, unchanged. **Commitment↔category coupling: deliberately NONE (owner, 2026-07-03)** — an auto-stamp hook at the `paid_txn_id` link moment was built and REVERTED; linking commitment payments to budget categories is deferred until commitments are properly implemented. Users link the generic way: tag the txn (register/rules/Lucius). RFC: `docs/rfc/commitments-and-funding-planning.md`.

**Credit-card engine (YNAB, ADR `2026-07-09-ynab-engine-credit-card-payment-envelopes.md`; the two-mode `credit_card_mode` flag was REMOVED 2026-07-10)** — payment envelopes are now the ONLY credit-card engine (the old "signed" mode, where a card's negative balance netted against on-budget cash, is gone — removed after the payment-envelope engine was verified YNAB-exact against real YNAB books). `cashflow.is_on_budget` stays the mode-agnostic derivation, now TYPE-ONLY with no override (ADR `2026-09-07-seven-account-types-one-axis`): **on-budget = `cash` + `credit`**, full stop — every `credit` account (not just `credit_card`; `is_payment_tracked_card` widened from ADR `2026-07-09`'s v1 `type=="credit_card"` frozenset) is payment-tracked, and `investment`/`fixed_deposit`/`retirement`/`receivable`/`loan` are all off-budget/tracking. Two facades split off `is_on_budget` — `is_cash_account` (feeds the RTA identity's cash side; type-only `cash` — a payment-tracked card, i.e. every `credit` account, is EXCLUDED — its debt no longer nets against cash) and `is_plan_source` (feeds envelope activity eligibility; IDENTICAL to `is_on_budget` — a card's own spending category still drains). `planning.sync_card_payment_envelopes()` (Commitments' sync as its template — real envelope via `envelopes.create_envelope`, pinned "Credit Card Payments" group, `account.payment_envelope_id` FK, `envelopes.is_card_payment_synced`/`force_delete_card_payment_envelope`, boot-ordered in `main.py` right after `ensure_envelopes_migrated`) mints ONE zero-category envelope per non-archived on-budget credit card, NO auto-target (starts at $0 — no auto-set-aside of pre-existing debt, so flipping the mode makes RTA jump by the outstanding balance of every payment-tracked card). **v2, COVERAGE-CAPPED** (replaces the deliberately-uncapped v1; the disposition of its uncovered remainder was rewritten 2026-09-08 and reverted 2026-09-09 — the coverage-cap mechanism itself never changed): `_iter_category_contributions` collects every payment-tracked-card expense as a candidate instead of crediting inline; `_capped_card_credits` resolves each spending ENVELOPE's pool in one batch — `moved = min(spend, max(0, envelope's Available BEFORE this month's card spends))`, resolved at the envelope (a merged N>1 envelope shares one pool) — and credits the covered amount to that spend's own card's payment envelope; the spending envelope still drains by the FULL spend regardless (its displayed Available goes negative for the uncovered part). A spend on an unlinked/blank category has no pool at all — moved is always 0 (a v2 tightening: v1 unconditionally credited even a blank-category spend) — and it yields no `_CARD_UNCOVERED_KEY` term either: with no envelope row there is no drain to cancel, so it is RTA-neutral by ABSENCE, exactly as neutral as the linked-but-unfunded case (restored 2026-09-09 after a one-day regression yielded the term unconditionally, making an unlinked card spend a bare subtraction that then evaporated at the next roll — the term is per-month, never carried). **The uncovered remainder is tracked by `_CARD_UNCOVERED_KEY` (restored; wire name `card_spend_not_covered`), which CANCELS the spending row's own drain** — so an unfunded card spend is RTA-neutral in-month (real debt, hasn't cost cash yet) AND stays RTA-neutral at rollover (never re-charged, unlike a cash overspend, which IS charged at rollover). A COVERED swipe is RTA-neutral because the set-aside relocates from the spending envelope to the payment envelope (both terms end where they started); an UNCOVERED one is ALSO RTA-neutral because `_CARD_UNCOVERED_KEY` cancels the drain the spending envelope would otherwise register — never manufacturing assignable cash out of unfunded debt, and never charging Ready to Assign for debt that hasn't cost cash yet. Rule 4 ("pre-existing/starting card debt does NOT reduce RTA") is RESTORED — the 2026-09-08 reversal (standing debt reduced RTA exactly like a freshly-uncovered spend, via continuous netting) is gone: a card's payment envelope starts at $0 and standing debt sits there, untouched by Ready to Assign, until the user assigns toward it — the native "pay a card off over time" mechanic (ADR `2026-09-09-ready-to-assign-follows-ynab-envelopes-are-the-category`). `_auto_cover_overspending` is likewise capped at the displayed Ready to Assign again (restored B4, symmetric with `_auto_underfunded`) — auto-assign can no longer propose funding money that doesn't exist. Payment envelopes remain the funding mechanism, unchanged: money moved into a card's payment envelope is cash set aside to pay it, and the real gap still surfaces via the payment row's own THREE fields (`is_payment_envelope=True`; each `None` on every other row) — `owed = max(0, −account_balance_as_of(card, month))`, read directly off the card's REAL ledger balance (`_payment_row_fields`/`_account_balance_base_as_of`), independent of the envelope walk so it reflects adjustment-driven debt too; `available_for_payment`, the raw signed Available (rule 3 — paying with unbudgeted money legitimately drives it negative, never clamped); and `underfunded = max(0, owed − max(available_for_payment, 0))`, whose INNER clamp is the identity's own `funded` clamp, so the row and Ready to Assign always name the same number (an overdrawn payment envelope funds nothing, but never owes extra on top of the balance its payment already knocked down). `owed` is on the wire in its own right (ADR `2026-09-08-ready-to-assign-is-unassigned-cash`) rather than left for a client to invert out of `underfunded + max(available_for_payment, 0)`: that inversion reads a paid-off card whose envelope still holds money as owing that money, which is exactly what made the Budget tab's optimistic Ready to Assign miss a release out of such an envelope (`useBudgetModel.cardOwed`). A card-paying transfer is UNCHANGED from v1: it drains the payment envelope by the TO-leg's own native amount (never `txn_base_amount`, which prefers the from-leg), UNCAPPED, and MAY drive it negative. `is_card_payment_synced` is wired into the SAME merge/split/delete/move_category guards `is_commitments_synced` uses (refused, `ValidationError`); `move_money` OUT of a payment envelope to `__rta` stays allowed (YNAB-faithful — unlike the other four ops). **Adjustment-leg blind spot (was a v1 "known limitation," now CORRECT v2 behavior):** `kind=adjustment` legs — including every account's own Starting-Balance opening transaction (ledger-tracking-start Phase 2) — are still invisible to the auto-move fold (adjustments never carry a category, unchanged) — this is now precisely rule 4's "starting debt" case: the payment envelope's Available correctly stays unaffected by it, and the real gap is surfaced honestly via `underfunded` (which reads the account's true balance, adjustments included). Since payment envelopes are the only engine, `main.py`'s boot syncs a payment envelope per on-budget card unconditionally; there is no mode flag to flip (the one-shot `migrate_credit_card_mode.py` flip script was removed with the mode). NOTE: flipping a pre-existing book onto this engine re-casts all historical card payments as payment-envelope activity (a card's raw Available goes deeply negative — "you paid this card with unbudgeted money, cover it"), which YNAB avoids by starting fresh; a fresh book never sees it.

**Pluggable budget engines (RFC `.claude/rfcs/2026-08-22-pluggable-budget-engines.md`, Phase 0/1 + the 2026-08-23 zero-based/envelope naming correction, Decision I)** — a paradigm-neutral `BudgetEngine` Protocol (`services/budget_engines/base.py`, `ENGINES` registry — two members: `zero_based`, `proportional`; a third, the strict cash-envelope method `envelope`, was removed 2026-09-25, ADR `2026-09-25-cash-envelopes-engine-is-removed`) sits ALONGSIDE everything above, never replacing it. **`zero_based.py`** (formerly `envelope.py` — the id `"envelope"` was a misnomer, since RTA-must-reach-zero is the zero-based rule, not the cash-envelope one) ADAPTS `planning.budget_month()`/`budget_health()` into the generic `ViewModel` (no math moved, equivalence-tested by `tests/test_budget_engine_equivalence.py` — the gate for the whole RFC) and keeps its native REST/UI/Lucius surface. **`proportional.py`** (id `proportional`, "50/30/20") is the second engine, and — since the 2026-09-25 owner redesign (ADR `2026-09-25-fifty-thirty-twenty-is-envelope-based-with-caps.md`) — its ROWS are ENVELOPES, the SAME envelopes Zero-Based uses (every live one except a credit-card payment envelope or a bot-managed/commitment-synced one), not categories: a book using both lenses now sees the same rows in both. Its per-envelope `activity` (2026-09-25 amendment) is gated through the SAME account-eligibility rule Zero-Based's own fold uses (`planning.plan_leg_ok`, reused verbatim rather than re-derived — a leg counts only on a known plan-source account, dated on/after that account's tracking start), which also flows into `history`'s four variants, `unassigned.no_envelope`, and `income.actual`/each income category's `last_month` (`income_by_category` applies the same gate to the income leg); a TRANSFER still never counts and an investment leg still isn't folded — both remain this engine's own prior, documented simplification (no Ready-to-Assign identity for a transfer's cash side to reconcile against), unchanged by the amendment. Each row's bucket resolves in precedence order — its own explicit `buckets[envelope_id]`; else, when the v1 `mapping` (below) has an opinion about at least one member category, the bucket that carried the most spend among those over the last 3 CLOSED months (ties -> needs > wants > skip); else `"unsorted"` — so an existing configured book keeps working with ZERO migration. Each row may also carry a per-month CAP, `caps: {envelope_id: [[month, amount], ...]}` — `cap_at(history, month)` reads the LAST entry at-or-before `month` (0/absent = no cap); setting one replaces every entry at or after that month with a single new one, so it's forward-only and a month before the real current calendar month is refused. Income is measured against `profile.monthly_net_income` for the current/future month (0 if unset), falling back to what was actually received in the counted income categories (`income_category_ids`, `null` = every income-kind category) for a CLOSED month, else the profile figure, else 0 — reported with `source: "profile"|"actual"`. Its **savings figure is still a RESIDUAL** (`income − needs − wants − unsorted − unassigned`, `unassigned` = spend in a category covered by no row envelope + genuinely uncategorized spend), never money moved into a savings/investment account; percentages are always "of income," and **income==0 forces every `Measure.percent` to `None`** (never a fabricated `0.0`) while **a negative savings figure is reported as-is, never clamped**. Its owned state now has five keys — `targets` (unchanged), `mapping` (v1, category->bucket, kept read-only forever for the fallback above), `buckets` (envelope->bucket, the live source of truth), `caps`, `income_category_ids` — still one `budget_engine_state` row (`db/budget_engine_state_store.py`); every verb (`configure`, `set_targets`, `set_bucket`, `set_cap`, `set_caps`, `copy_targets_to_caps`, `set_income_categories`, plus the legacy `set_config`) returns only the top-level key(s) it changed, and `service.py::apply_verb` shallow-merges that delta onto the engine's current row before persisting — the mechanism that lets `caps`/`buckets`/etc. survive a call to a DIFFERENT verb untouched. `compute_month()` (`proportional_fold.py`) is the ONE computation both `GET /api/planning/proportional/month` (the screen's own contract: envelope rows with bucket/cap/activity/pace-history, income, the income-category picker, unassigned spend) and `fold()`/`get_budget_view` (Lucius, and the generic `ViewModel` — needs/wants groups carry every bucketed row as measures `activity`/`pct_of_income`/`cap`/`left`; a skip/unsorted row and the unassigned figures fold into `unmapped`, individual rows riding on the new `Unmapped.rows`) build on, so the two can never silently disagree. `draft()`/`GET .../engines/proportional/draft` stay CATEGORY-level (v1, unchanged, kept for wire compatibility); `configure` seeds an ENVELOPE-level bucket for every row that has none via the SAME underlying keyword+stability heuristic (`proportional_draft.draft_bucket`, applied to the envelope's own name + its member categories' combined history), EXCEPT the heuristic's own "don't know" (`skip`, only ever returned low-confidence), which is left UNSET so the row reads `unsorted` — To sort asks, and its spend still counts against savings; Excluded is only ever chosen, never seeded (ADR amendment 2026-09-25) — its history/stability math lives in `draft_signals.py`, shared with zero-based's target sizing — no LLM, no network. REST (`api/planning.py`): `GET /api/planning/engines` (descriptors + home + configured), `GET /api/planning/view?engine=&ym=` (any engine's `ViewModel`, default home/current month), `GET /api/planning/engines/proportional/draft?ym=` (preview only), `PUT /api/planning/engines/proportional/config` (validates `needs+wants<=100`, every bucket in `{needs,wants,skip}`, every category ref resolvable — `services/budget_engines/proportional_config.py`; v1, kept for wire compatibility), `GET /api/planning/proportional/month?ym=` (2026-09-25: the screen's own envelope-row contract, `services.budget_engines.service.proportional_month`). The home-lens switch itself (`plan_state.payload["budget"]["home_engine_id"]`, unset reads as `"zero_based"` for a book that has ever assigned and `"proportional"` for one that never has, and a stored id that no longer names a registered engine reads as unset) is now WIRED (**Phase 2**, Decision A/E): `POST /api/planning/home-engine` (`{engine_id}`) and the AI tool `set_home_budget_engine` (`mutates=("budget",)`) both call `services.budget_engines.base.set_home_engine_id`, which validates against the real `ENGINES` registry (404/`NotFoundError` naming the real ones for an unknown id — writing garbage here would brick the Plan tab) THEN persists via `db/plan_state_store.py`'s `PlanStateStore.set_home_engine_id` — the SAME locked read-modify-write `add_scenario`/`set_baseline` already use on this singleton row, so a lens switch is checkpoint-covered and `/rewind`-able like any other user edit. Switching touches EXACTLY that one key — no other engine's own state (`budget_engine_state` rows, `budget_assignments`, `envelopes`, …) is ever read or written, proven directly (not merely asserted) by `tests/test_budget_engines_base.py::test_switching_home_and_back_leaves_every_engines_state_byte_identical`.
