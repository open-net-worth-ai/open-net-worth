# AI tool conventions — schemas, naming, errors, classification, offers

> **On-demand reference.** Not loaded into every turn — read it when you touch this area.
> Decisions and their reasoning live in [`docs/adr/`](../adr/); this file states current truth.

Add a tool → one `@tool`-decorated async handler in `ai/tools/<group>.py`. Registry auto-collects. No hand-maintained schema list.

**`input_schema` may be DERIVED from a typed model instead of hand-written** (ADR `2026-07-19-derive-tool-schemas-from-models`) — the fix for the root cause behind the S2 error contract's "the declared schemas do NOT describe what the handlers accept". `ai/tools/schema_from_model.py`'s `schema_of(Model, tool_name=…)` projects an Anthropic-shaped schema from a `ToolInput` (Pydantic) subclass via five transforms: inline `$defs`/`$ref`; collapse `anyOf[X,null]`→`X`; drop `title`; drop `default: null` (a REAL default survives); drop the class docstring Pydantic promotes to a root `description`. Every walk is **structure-aware** — `create_artifact`/`schedule_task`/`update_scheduled_task` have a parameter literally NAMED `title` and `forget_fact` one named `description`, so the keyword classification is imported from `registry._SCHEMA_*_KEYWORDS` rather than re-declared. Migration is **additive and incremental**: a derived tool registers alongside a literal one with zero `registry.py` changes (mixed registry proven). `tests/golden/tool_input_schemas.json` pins what all 272 tools emitted pre-derivation and `tests/test_schema_from_model.py::assert_derived_matches_literal` asserts byte-identity for migrated tools + no drift for the rest — so converting is convert→assert→move-on, and a mismatch is a red diff, never a silent behaviour change. The golden file is deliberately NOT auto-regenerated (editing it by hand IS the review moment). **A green assertion proves no CHANGE, never CORRECTNESS** — where the pinned literal is wrong, byte-identity preserves the wrongness; fixing a schema is its own commit. **Migrated so far: 251 of 272 (92%)**, across every unrestricted `ai/tools/` module (accounts, categories, alerts, alpaca, connectors, model_config, memory, scheduling, scripts, skills, code, profile, plan_scenarios, xray, income, external_mcp, prices, rebalance, reports, aggregation, audit, artifacts, routing, watchlist, intel, envelopes, options, planning, portfolio, lots, equity, payees, ledger, commitments, agents, rules, matching, screen, imports, plus the original 5 proof tools) — a partial file migrates its clean subset, leaving the quirky remainder as literals. `schema_of_no_required(model, tool_name=…)` is the Phase-2 helper (mirrors `explicit_null`): omits the root `required` key entirely rather than defaulting to `[]`, for the 7 tools whose literal spells "nothing required" that way (`list_scheduled_tasks`, `list_import_batches`, `delete_transactions_where`, …) — refuses a model that actually declares a required field. Re-measured inventory (now historical): **222 of 272 tools (81.6%) are structurally clean** (NOT the 96% an earlier sketch claimed — it missed nested objects under `items`); the quirk classes and per-class policy are in the ADR. Both quirk-class blockers that inventory flagged are now CLOSED, promoted into `schema_from_model.py` proper as two reusable escape hatches (a prior lane duplicated the first as a local `_bare_object_schema` helper in three files before promotion — see the ADR's lane log): (1) **`bare_object_schema`** — a `json_schema_extra` callable for a nested field whose literal is a BARE `{"type":"object"}` (no `properties`, no `additionalProperties` at all — e.g. `commitments`' `installments`/`funding_plan`/`actions`, several `changes`/`input`/`params` bags). A plain `Dict[str, Any]` always emits `additionalProperties: true`, a byte mismatch; the callable strips it back out, recursively, wherever the field's actual shape puts it — the field itself, an `Optional` wrapper's `anyOf` branches (the non-obvious part: Pydantic hangs `json_schema_extra` off the OUTER `anyOf[X,null]`, not the inner `X`), a `List[...]`'s `items`, or both composed. (2) **`NestedInput`** — a base for a NESTED model (never the tool's own root) whose literal declares `properties` but omits `additionalProperties` entirely, because the author never wrote one; a plain (non-`ToolInput`) `BaseModel`'s default `extra="ignore"` emits no such keyword, matching exactly. Both are shared, tested (`tests/test_schema_from_model.py`), and used across every subsequently-migrated tool with a batch-item/stored-dict shape. The `type: ["x","null"]` nullables (`update_transactions`' per-row `payee_id`, `create_payees.default_category`, and `set_payees_default_category.category`) are the one remaining quirk class, migrated LAST via `explicit_null()` with a human decision — there, an explicit `null` CLEARS a money field while omission leaves it untouched, so a blind collapse to `{"type":"string"}` would be a silent semantic change; `explicit_null()` itself is still unused in any live tool, by design. **`payees.py` re-measured against the two escape hatches above (2026-07-19, a later lane): the earlier "batch shape isn't cleanly expressible" call was WRONG once `bare_object_schema`/`NestedInput`/the bare-`Union[str,List[str]]`-with-`default=None` technique existed** — 13 of its 15 tools (all but the two explicit-null ones, `create_payees`/`set_payees_default_category`) migrated cleanly, including a double-nested case (`set_payees_rules`'s `RuleSpec` reused as both the broadcast `rules` field's item type and each `updates[].rules` entry's item type). Lesson for future re-measurement: a "not cleanly expressible" call is only as good as the mechanism at the time it was made — re-check it once the mechanism grows. See the "Tool renames" note below for the migration bookkeeping.

**A tool's `input_schema` must never carry `oneOf`/`allOf`/`anyOf` at its OWN top level** — Anthropic's tool-use API rejects that unconditionally (HTTP 400 on the very first message, not an opt-in strict mode), and since `find_tools` is a CORE tool loaded in every session, this once broke every session for anyone on the raw Anthropic API-key transport the instant it was added (owner-reproduced live, 2026-09-03). It was added there specifically to express a cross-field "at least one of query, names" constraint that plain `required` can't — verified only against OpenAI's Structured Outputs docs (which do allow root-level `anyOf`), never against Anthropic, which is what actually shipped and broke. **Enforced, not just documented**: `tests/test_schema_from_model.py::test_tool_schemas_never_use_top_level_oneof_allof_anyof` walks every registered tool's derived schema and fails the build on any offender — runs in the normal (non-integration) suite, no network, no API key. A NESTED `oneOf`/`allOf`/`anyOf` (inside a property — e.g. an `Optional` field's `anyOf[X, null]`, which `schema_of`'s own transforms already collapse away) is fine; only the schema's own top level is the landmine. **The fix for a genuine cross-field "at least one of" need**: state it in the tool's top-level `description` in plain language (`find_tools`'s own description: "REQUIRED: pass exactly one of the two below — never call this with neither"), and let the handler's existing runtime validation catch a call that ignores it — never reach for a schema-level boolean combinator to enforce it, on any provider, without first proving that specific provider's REAL API tolerates it (a doc citation is not proof; the OpenAI citation here was directionally right for this app's actual non-strict tool-calling mode, and still wasn't enough — it was never checked against Anthropic at all).

**Tool NAMING rules — ENFORCED, not documented (`make lint` runs `backend/scripts/tool_inventory.py --lint`, which exits NON-ZERO on any defect).** Four lanes drove this surface from 80 naming defects to 0 and nothing stopped the 81st, so the linter is now a blocking gate rather than a report. It lives in `lint` (not `check`) for the same reason import-linter does: a static contract check over the registry, no server, no fixtures — and `check` runs `lint` first, so one placement covers both. Three rules, each with an explicit REVIEWED exemption table rather than a heuristic (a heuristic cannot tell these apart; a person can, once):
1. **Entity-set arity.** Is the array the SET OF ENTITIES the tool acts on, or an ATTRIBUTE of one entity? Entity set → tool name AND param plural (`update_accounts(updates=[…])`). Attribute of one → correctly singular (`update_grant(tranches=[…])` — one grant, many tranches). Exemptions: `ATTRIBUTE_LIST_PARAMS`. Uncountable objects (`move_money`, `assign_budget`) are exempt via `UNCOUNTABLE_OBJECTS`, with the reasoning recorded there.
2. **`create_` vs `add_` (2026-07-19d).** **`create_` mints a STANDALONE entity; `add_` inserts into a NAMED PARENT.** `add_watchlist_items(watchlist=…)` and `add_payee_aliases(payee_id=…)` are correct — each names the parent it inserts into. `add_account` was not: an account has no parent, so the name asserted a containment relationship the data model does not have. Renamed → `create_account`. The service layer already had this right (`services/categories.py::create_category`), and the collision is real — `services/envelopes.py::add_category(envelope_id, category_id)` is a *correct* add (linking an existing category into a parent envelope, exposed as `link_category`). Applying a verb by what it does to the object graph, not by taste. **Not yet machine-enforced**: `add_categories` violated it (a category has had no parent since the envelope⊥category split) — renamed `create_categories` 2026-09-26, with `remove_categories`→`delete_categories` by the same reasoning (`remove_` detaches from a parent; a category is deleted) and `add_transactions`/`add_news_sources` are borderline — a linter rule would fail on tools outside this lane's scope, so the rule is written here and the violators are on `docs/launch/BOARD.md`. Adding the check is the follow-up, once those are decided.
3. **No dual-shape duplication.** A batch array must not be advertised alongside a root-level copy of its own item fields — two spellings of one call is a fork carrying no information, and a half-mix (a bare `payee_id` beside an `updates` array) type-checks while meaning something nobody designed. `update_transactions` is the settled shape: advertise the array, keep accepting the bare form in the handler, leave that leniency UNDOCUMENTED. `schema_from_model.schema_of_batch_only(Model, array=…)` applies it (35 tools, 2026-07-19d) — it un-advertises without removing, since `registry.dispatch` validates effective TYPE only and never enforces `additionalProperties`, so every stored bare caller keeps working (pinned by `tests/test_batch_only_schemas.py`). Exemptions: `BROADCAST_VALUE_TOOLS` — 10 tools where the root field is the broadcast VALUE paired with a plural ids param (`set_payees_hidden(payee_ids=[…], hidden=true)`); stripping it would leave nothing to broadcast and silently write a no-op.
Also enforced: **a tool description may not name a dead tool.** A description is the model's map of the surface — "then call `add_transaction`" makes the model call a name absent from the catalog and every schema. There is no alias to absorb it any more, so it fails immediately rather than drifting invisibly; either way the instruction is one the harness taught. Renaming a tool must fix the SENTENCES about it too. Both tool and param descriptions are swept.

**RENAMING a tool is a DATA MIGRATION — a tool name is PERSISTED data, and there are no aliases** (ADR [`2026-08-25-tool-names-are-final`](../adr/2026-08-25-tool-names-are-final.md)). Names live in the `automations` table, skill instructions, backups, exports, and in-flight transcripts. The procedure: rename the tool, add the pair to `backend/scripts/migrate_tool_names.py`'s `RENAMES`, then RUN it (`--apply` writes after a timestamped backup; it rewrites a SKILL.md's body prose as well as its frontmatter, because a dead name in the instructions is a broken instruction too). Nothing resolves an old name at runtime — after the rename it is an unknown tool and says so, loudly, which is deliberate: the mechanism this replaced made a stale name silently invisible instead (the 2026-07-18 outage). Agent/scheduled-run scopes validate these names loudly. Skill `allowed-tools` / `disallowed-tools` values are different: they round-trip as inert compatibility metadata, never degrade or hide a skill, and never alter offer or dispatch. Regression suite: `tests/test_tool_name_migration.py` against `tests/fixtures/playbooks/` (never the live data dir).

**Tool error contract (S2).** Three layers, all pinned by `tests/test_tool_error_contract.py`. (1) **`is_error` reaches the model** — `assistant._tool_result_block()` is the ONLY constructor of a `tool_result` block and stamps `is_error: true` (never an explicit `false`) whenever the content is the structured `{"error": …}` shape; `_tool_error_message()` is the ONE detection, shared by the `tool_error` log line, the audit step's `ok` flag, and this flag. A forced `is_error=` overrides detection — used to flag the plain-text tripwire DROP (a hard refusal) and to suppress the flag when a proposed/deduped call replaces the content with a control message. The extra key is inert downstream: `rehydrate_messages` and the OpenAI adapter read only `tool_use_id`/`content`, the frontend never sees the block (it renders the `tool_done` SSE `result` string), and `is_error` is a valid Anthropic tool_result field. (2) **`registry.dispatch` type-validates input** before entering the handler, returning a pointer-precise `{"error": …}` (`expected number, got str at splits[0].amount`). It validates the **EFFECTIVE** type only — what a handler could actually consume — because the declared schemas do NOT describe what the handlers accept, and every stricter reading was measured to break working calls: `additionalProperties` (the propose→apply replay paths dispatch a stored change dict verbatim, carrying `type`/`display`/`reason`/`idempotency_key`), `required` (stale lists — `add_transaction` names the legacy single-leg shape and `category`, which is optional by invariant), `enum` (handlers coerce by design, e.g. `get_returns`→1Y), and strict `type` (`_coerce_obj` accepts stringified objects, `abs(float(x))` accepts `"12.50"`, and an explicit `null` means "omitted"). Widening the enforced set means FIXING THE SCHEMAS FIRST. (3) **Errors carry the recovery path** — `core.errors.recovery_hint(value, candidates, tool_hint=…)` (stdlib `difflib`, leaf-safe) appends the closest existing values plus the tool that lists them; call sites keep their own head sentence and only ever build it on the ERROR path (no lookup on the happy path). Wired at the unknown-category and unknown-account legs in `services/ledger.py`; `payee_registry.require_payee` already pointed at `get_payees`.

**Tool write classification (MANDATORY, `tests/test_tool_domains.py`).** Every registered production tool must be explicitly classified as exactly ONE of: (1) `mutates=(domains…)` on its decorator — it CHANGES something of the owner's, (2) `refreshes=(domains…)` — a READ that only makes a screen refresh (a last-synced stamp, a raw-evidence snapshot, a memoized result): it reaches `data_changed` exactly like `mutates=` but is NOT a write, so it does not ask by default; a tool declaring both is refused at registration, and `tests/test_tool_domains.py::REVIEWED_REFRESHING_READS` pins the members because the tag removes the tool's approval default, (3) `READ_ONLY_TOOLS` (reviewed — writes nothing persistent), or (4) `NO_DOMAIN_WRITE_TOOLS` (a real side effect with NO local data domain a view could refetch — `email_send_message` (outbound SMTP, `external_effect=True`), `find_tools` (turn discovery state + session meta/telemetry), `activate_skill` (durable instruction/resource activation; it does not change tool policy), `run_script`/`run_code` (sandboxed subprocess, no store access; both `external_effect=True`), `run_screen_command` (ephemeral UI state)). **The SEED value of a tool's permission row follows this classification, for built-in and connector tools alike** (ADRs `2026-10-11-tool-defaults-follow-what-a-tool-does`, `2026-10-11-permissions-are-one-value-per-tool`): a tool that writes (`mutates=`) is seeded Ask (`needs_approval`) UNLESS every domain it writes is a **workspace domain** (Lucius's own notebook, not the owner's book: `_confirm_gate.WORKSPACE_DOMAINS` = `memory skills artifacts notification_log`, declared once per DOMAIN and checked against the tool's `mutates=` — a write mixing a workspace domain with any other still asks, and no domain information is never read as workspace); a tool declaring `external_effect=True` (it acts outside the owner's data: `email_send_message`, `telegram_send_message`, `webhook_send_message`, `run_script`, `run_code`) is seeded Ask whatever it writes; anything else is Always allow — there is no name list of exempt reads or workspace writes. A new write whose domains are all workspace therefore starts Always allow with no further step; a new domain that is the assistant's own notebook is added to `WORKSPACE_DOMAINS` (a reviewed decision). A tool that does something outside the owner's data declares `external_effect=True` on its decorator — never a name in a list. A tool whose whole feature can be switched off (the code sandbox) declares `unavailable=<callable returning a refusal or None>`: dispatch refuses a fresh call at once, before the judge or any card, and the handler re-checks on redemption. Every tool has exactly ONE value (Always allow / Ask / Block) — `services.tool_permissions.sync_seeds` gives each a row at boot, `seed_level` is the one seed rule (what a fresh row gets, what Reset restores, what dispatch falls back to for a tool with no row yet), and the owner's value wins for a read as much as a write; the approval mode only decides what Ask means. There is no name list of tools the mode or the judge skips (the four Automation tools follow the mode like any other; the judge is told the consequence of an Automation call in a server-written line instead); `registry.mutated_domains(name)` (mutates + refreshes) is the FRESHNESS answer and must not be used to decide whether a tool asks. External MCP tools are outside the registry, start at `needs_approval`, and then take the SAME chain as every registry tool (`ai.assistant._dispatch_external` → `_confirm_gate.external_decision`; the manager only carries the decision out via `call` / `fire_allowed`). `web_search` and `fetch_page` belong to the ACTIVE search connector: their permission key is that provider's own tool (`_connector_gate.permission_key`), never a `core:` row of their own. There is no unclassified state and NO naming shortcut — the sweep is name-blind, because a `get_`/`list_`/`propose_` prefix proves nothing: `get_watchlist` re-syncs My-holdings membership, `get_live_prices` records into the `price_points` table, `list_match_reviews` sweeps zombie reviews, `diff_statement`/`verify_statement_balance` memoize onto the statement/batch record, `propose_position_update` find-or-CREATEs an account, `propose_lot_dispose` seeds an opening lot. Adding a name to an exempt set is a REVIEWED decision (trace the handler through its service/store calls first), never a way to silence the test. **Deliberately out of scope for `mutates=`** so the tag stays a data-refresh signal: telemetry + conversation bookkeeping (`cost_log.json` — written by every LLM-touching tool — the tool-discovery log, chat session meta). **CORRECTION: `dispatch_to_agent` no longer exists** — it was the Agent product's own full-turn dispatch tool, deleted whole with the rest of that surface (`d0da1a09 feat!: retire the Agent product`, 2026-08-02; see "Automations" in `docs/ai/TOOL_CATALOG.md`). No current tool carries a `mutates=("*",)` wildcard as a stand-in for "runs its own dispatch loop" — a scheduled Automation run dispatches through the SAME loop as an interactive turn (`ai/turns.py`) and its writes' domains DO reach that run's own `data_changed` aggregation. Domain vocabulary in use (re-verified against `mutates=` in `ai/tools/*.py`): `accounts alerts artifacts automations budget categories commitments config corrections income intel ledger memory news_sources notification_log options payees plan portfolio profile receipts sandbox skills uploads watchlist` + `*`. `agents`/`rules`/`signals`/`tasks` are RETIRED domain tags (folded into `automations`, or the `signals` table itself was renamed `notification_log` on 2026-08-20, revision 0044 — `intel` is still the separate `intel_signals` table, unchanged).

**Connector discovery gating (`connector=`, RFC `.claude/rfcs/2026-08-10-connectors-architecture.md` §B2, 2026-08-13).** A tool scoped to ONE connector carries `connector="<id>"` on its `@tool` decorator (e.g. `connector="plaid"`, `connector="web_search:tavily"` — the exact id `services.connectors.list_connectors()` uses for that connector's own card), the DISCOVERY-gating twin of `mutates=`. `ai/tools/_connector_gate.py::hidden_connector_tools()` reads `registry.connector_tagged_tools()` + `services.connectors.enabled_connector_ids()` (one `list_connectors()` call, computed once per catalog build / `find_tools` call, never per-tag) and returns every tagged tool whose connector isn't enabled; `ai/tools/catalog.py`'s flat system-prompt catalog and `ai/tools/_groups.py`'s `find_tools` (both `query=` search and exact `names=` load) exclude that set the same way `_CATALOG_HIDDEN` already excludes the deferred Tax tools. Fails CLOSED on any enablement-lookup error (hides every connector-tagged tool rather than guessing). **Discovery-hiding is not itself a dispatch/execution gate** — a connector-tagged tool already loaded, or called directly by an exact name the model already knows, still dispatches regardless of catalog visibility; a disabled connector's own handler reports its own `status: "disabled"` (same self-reporting contract every aggregation provider already has) rather than needing a hard block here. **But since the 2026-08-14 permission-store merge, the SAME `connector=` tag is also the JOIN onto the permission table**: `ai/tools/_connector_gate.py::permission_owner()` reads it to resolve the tool's OWNER (falling back to the reserved `core` bucket for an untagged tool), and `ai/tools/_confirm_gate.py::effective_level()` reads that owner's stored level from `services.tool_permissions` before every dispatch — so the tag now has two independent effects, not one: it hides a tool from the offer/search surface while its connector is off, AND it names whose permission decision governs the call. `tool_grants`/`ToolGrantStore`, the separate binary mechanism that used to answer the permission question, is DELETED (absorbed into `tool_permissions`, ADR `2026-08-14-one-permission-store-for-every-tool`). An untagged (internal) tool is unaffected by discovery-hiding, but is not exempt from a permission decision — it is simply owned by `core`. A tool spanning several connectors (or none cleanly) — the bulk `get_connector_status` (its sibling bulk `connector_sync` is RETIRED outright, RFC `connectors-as-data-sources`, no single-tool replacement — see `backend/scripts/tool_renames.py`), the generic `web_search`/`fetch_page` — deliberately carries NO tag and is therefore never gated, by documented convention (see each module's own docstring), not an oversight: a single connector id doesn't fit a multi-connector convenience tool, and gating it off would remove the one path that still works before any single provider is configured. First applied promoting the aggregation providers' per-provider tools (`plaid_fetch_transactions`, `ibkr_get_status`, …) and the new per-web-search-provider tools (`tavily_search`, `serper_fetch_page`, …) back to first-class, separately-schema'd tools — see `ai/tools/connectors.py`'s, `ai/tools/connector_fetch.py`'s, and `ai/tools/web_search_providers.py`'s module docstrings for the full history.

Interactive default offer is an explicit small core (`CORE_TOOL_NAMES` in `ai/tools/_groups.py`, ~13 hot read/write tools — cut from ~20 by the 2026-07-19 evidence-based CORE diet, `docs/adr/2026-07-19-core-tool-offer-diet.md`, gated on MEASURED per-tool session-spread over the real ~293-session corpus rather than intuition) — not "everything minus rare". Every other tool is discoverable via a compact catalog auto-generated from the registry by `ai/tools/catalog.py` (grouped by source module) and loaded on demand by the model calling `find_tools(query="…")` (keyword search — the `groups=` load path and the `TOOL_GROUPS` table were removed 2026-07-18); loaded tools are sticky per session (persisted in session meta as `extra_tool_names`). External-MCP tools are excluded from the default offer and are search-gated (appended only once loaded); at MCP scale the catalog lists a large server as ONE roster line (`External (srv): N tools — find_tools(query=…)`) instead of every tool (adaptive in `catalog.py`: small server listed tool-by-tool, large server collapses), so the cached prompt stays flat. **Discovery gate** (the universal loader, `assistant.py` dispatch loop): if the model calls a tool that isn't loaded yet, it is NOT executed blind — a known tool (internal or external-MCP) is auto-loaded (`add_extra_names` + persist) and the model is bounced with "call it again", so the retry uses the real schema; a hallucinated name is refused. An external-MCP tool follows the same rule as an internal read: if our own name classification says read (`mcp_external.is_provably_read_only` — server `readOnlyHint`/`destructiveHint` can only veto, never grant) and its args validate STRICTLY against the `inputSchema` discovered in the handshake (`assistant._external_gate_verdict`, outcome `executed_external`), it proceeds on that first call into the ordinary external dispatch, where `tool_permissions` still decides (blocked/ask-stage/allow) exactly as on a retry; no discovered schema, a non-read tool or invalid args bounce (ADR `2026-10-03-external-mcp-discovery-gate-validates-against-discovered-schema`). This makes `find_tools` optional for internal tools (just call them) while staying essential for searching the un-cataloged external long tail. A known tool is auto-loaded regardless of caller class; a hallucinated name is still refused. (Before 2026-07-18 this gate was interactive-only, because a separate default-deny block refused any off-scope name on headless/skill turns first — that block and the tier boundary it enforced are GONE, see ADR `2026-07-18-remove-layered-ai-permission-system`.) `ONW_FULL_TOOL_OFFER=1` restores the full offer. `backend/mcp/adapter.py` and `backend/api/agents.py` still see the full `TOOL_SCHEMAS` registry — never filter it.

Same evidence bar the owner already applied when REJECTING promotion of the five most-bounced tools ("just web search is fine, get screen detail is fine, but the rest, i don't think so") — applied symmetrically to demotion. Net effect on this real account, measured end to end (system + CORE tools + turn context, real tokenizer): **23,337 → 20,925 tokens (−10.3%)** for a first "hello" turn; the residual gap to the owner's reported 33,881 is most likely the frontend's per-screen context snapshot (ADR 0028, rides the user turn, `frontend/` — out of scope for this lane) and/or the owner's turn having gone through the actually-configured chat provider (`openai_compatible` via OpenRouter, `x-ai/grok-4.5` per `model_config.json` — a different tokenizer than Anthropic's, which is what `count_tokens` measures).

**Agent/scheduled runs get the SAME lazy machinery** (ADR `2026-07-19-agent-runs-lazy-tool-offer`) — measured incident: an agent's `allowed_tools` used to expand to FULL inline schemas on every model round trip of every run (the live "Transaction & Trade Logger" agent, 143 listed tools / 135 resolved schemas, sent 156K+ chars inline every round — 4x the interactive CORE offer). The discovery gate used to be structurally unreachable from an agent turn (it only fired when `_skill_scope.offer_tool_names() is None`, and an agent run always sets that offer), so bounding the OFFER without first fixing the GATE would have bounced the model forever — the gate is now the load-bearing half of this fix, not the offer shape. **`ai/tools/_agent_offer.split_agent_offer`** is the bound: an agent whose tool count is at or under `len(CORE_TOOL_NAMES)` (~13 since the 2026-07-19 CORE diet, down from ~20 — the interactive cold-start size) is delivered in full, unchanged (a short list is already cheap and IS the point of a narrowly-scoped agent); a LARGER agent gets a bounded inline slice — its own CORE-overlapping tools (re-measured against the smaller set on the same live `agents.json`: 9 of Fraud Detection's 64 and 10 of Trade-Logger's 143, down from 14/16 of the old 20-tool set — a big agent's hot path is usually CORE's hot path too) + `find_tools` (added even when the agent never listed it) + enough of the rest (alphabetical, for a cache-stable prompt) to fill the same ~13-tool budget — plus whatever THIS turn's discovery gate has additionally loaded. `assistant._build_agent_offer` is the `_active_tools()` branch that assembles this; `assistant._auto_load_and_verdict`/`_gate_bounce_message` are the load/verdict/bounce-message helpers the dispatch loop now shares between the interactive path and this one. **Reach never shrinks**: every tool in a large agent's own `allowed_tools` stays reachable within the SAME turn via the identical auto-load-then-validate lazy path (a valid-args read executes in one round trip; a write, or invalid args, bounces once then executes on the loaded retry) — a name OUTSIDE the agent's own list is left untouched by this gate exactly as before (falls through to normal dispatch unchanged; this gate has never been the thing that refuses an out-of-offer call, and still isn't — ADR 2026-07-18). `find_tools` itself is scoped the same way (`ai/tools/_groups._reachable_universe`): under an active explicit offer, `find_tools(query=…)`/`find_tools(names=[…])` can only ever surface a tool inside that SAME offer, never the wider registry — otherwise granting every bounded agent implicit `find_tools` access would itself have been a reachability widening. The agent system prompt (`build_agent_system_prompt(allowed_tools=…)`, threaded from `main._scheduled_agent_runner`) gains a scoped tool catalog (`ai/prompts._fmt_agent_tool_catalog`) naming (never describing) the agent's own not-yet-inlined tools, appended to the prompt's STATIC/cacheable half — without it the model has no way to know a lazy tool exists unless its own hand-authored `prompt` happens to name it. A tool loaded mid-run survives every remaining round of that SAME run (the `ai/tools/_extra_groups_scope` ContextVar lives for the run's one `asyncio` Task) but never across separate scheduled fires (each mints a fresh `scheduled-<uuid>` session, `clear_session()`-ed at the end) — by design, so an edited `allowed_tools` takes effect on the very next fire instead of being masked by a stale loaded-set. Verified end-to-end (not just unit-level) in `tests/test_agent_lazy_run_e2e.py`, which drives a 271-tool synthetic agent through the REAL `services.agents.run_agent` → the REAL `main._scheduled_agent_runner` (registered on the production seam) → the REAL `assistant.run` dispatch loop.

**Per-turn tool PERMISSIONS — REMOVED 2026-07-18** (ADR `2026-07-18-remove-layered-ai-permission-system`). The enforcement is gone: `_headless_scope` and `_responder_scope`, `_scope_block_reason`, and the dispatch-loop default-deny block are all deleted. Nothing refuses a tool by caller class any more — a scheduled task, an agent run, an inbound MCP call, a skill turn and an interactive chat turn may all write. What REMAINS is the mundane job that ceiling was also doing: telling a non-interactive caller's turn which tools to OFFER, since it has no session-sticky `find_tools` history to build an offer from. `_skill_scope._offer_scope` (set via `set_offer_scope`) is that explicit, caller-supplied offer — an agent run passes its own `allowed_tools`; the P3-AG5 reflection pass passes an EMPTY set (so `None` ≠ `frozenset()` — never collapse them with `or`); a scheduled `prompt_lucius` passes nothing and gets the same default offer a chat turn gets. It shapes `tools=`, it does NOT refuse a call. The SKILL scope survives on the same terms (offer, not ceiling), as does `snapshot_scope`/`restore_scope` (the CONC-H5 nested-turn fix). `allowed_tools` on an agent is CONFIGURATION — what this agent is pointed at, and therefore what it can do — not an enforced ceiling; do not reintroduce it as one. **There is no "unattended" signal any more** (2026-10-11). `core.unattended` and the `script_skills_unattended_enabled` switch were deleted: whether a call asks is the tool's permission value plus the approval mode, decided identically in a chat and in an Automation run (ADR `2026-10-11-permissions-are-one-value-per-tool`). The only feature switches left are `code_execution_enabled` and `script_skills_enabled`.

**`create_account`/`update_accounts`: `type` is a seven-value enum, and nothing else classifies an account** (ADR `2026-09-07-seven-account-types-one-axis`). `_AccountType` (`ai/tools/accounts.py`) is `Literal` over `cash | fixed_deposit | investment | retirement | receivable | credit | loan`; the field description gives each value's one-line meaning (spendable/on-budget for `cash`, "holdings + settlement cash" for `investment`, etc.) so the model never has to guess from a bare enum token. `kind`, `asset_class`, `locked`, `on_budget`, and `group` are REJECTED parameters, not silently-ignored ones — they were removed from `CreateAccountInput`/`UpdateAccountItem` entirely, so a caller (or a stale skill/agent prompt) that still passes one of them fails schema validation loudly rather than having it dropped on the floor. `apr` is described as "interest rate % — credit and loan accounts" now that it is the one fact that distinguishes a loan's behavior instead of a dead subtype.
