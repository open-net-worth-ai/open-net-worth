# AI tool catalog — NON-AUTHORITATIVE snapshot

> **The registry is the source of truth, not this file.**
> Tools are auto-collected from `@tool` handlers in `backend/ai/tools/`. To find a tool:
> the model calls `find_tools(query=…)`; a human runs
> `.venv/bin/python3 -m backend.scripts.tool_inventory`.
>
> This snapshot is kept only as a browsable overview and **will drift**. Never treat a
> name here as proof a tool exists.

All `@tool` handlers in `ai/tools/`. **Every tool is callable by every caller** — interactive chat, a scheduled task, an agent run, and an inbound MCP call all see the same surface. There is no headless/interactive split, no tier, and no per-agent grant (removed 2026-07-18, ADR `2026-07-18-remove-layered-ai-permission-system`). What still varies per tool is whether it is in the default offer (`CORE_TOOL_NAMES`) or discovered via `find_tools`, and whether it renders a `ChangePreview` confirm card — the card is a legibility affordance, not a gate.

**Ledger:** `add_transactions` (was `add_transaction`; a single plural tool — there is no separate `bulk_add_transactions`), `get_transactions` (25 rows default; `summary_only` for exact totals with no rows; PLURAL `account_ids`/`category`/`tag`/`payee_id`/`transaction_type` + `q_field`), `update_transactions` (merges `update_transaction` + `bulk_update_transactions` — see below), `delete_transactions` (soft-delete by explicit id list, no `confirm` flag), `bulk_delete_transactions` (the DESTRUCTIVE-protocol twin — same id-list shape, but REFUSES unless `confirm=true`), `delete_transactions_where` (filter-based sweep, no id list — see the "known gap" note below), `import_transactions`, `get_ledger_summary`, `get_spending_summary`, `get_spending_breakdown` (a window's spend split into recurring bills vs day-to-day, vs the prior and the usual period — server-computed, so report skills quote it instead of totalling rows), `get_uncategorized_summary`, `trace_transactions` (was `trace_transaction`, batch-renamed 2026-07-19; old name still resolves as an alias), `add_transaction_refs` (CDS-5 — see below)

**`add_transaction_refs(transaction_id, refs=[{source, ref}])` (ADR `2026-09-07-provenance-refs-attach-by-tool-detach-with-decision.md`, CDS-5)** — links an existing row to a provider/email record it was booked WITHOUT, closing the loop the strong-duplicate refusal opens: when a fetched row collides with a hand-typed transaction, `services.ledger._duplicate_error`'s refusal (single-add AND bulk pre-flight alike) appends a THIRD exit naming this tool with the exact `{source, ref}` pair filled in, ONLY when the incoming row itself carries external refs (`core.errors.duplicate_hint`'s `attach_hint`). The service choke (`services.ledger.attach_external_refs`) refuses a pair a DIFFERENT live row already holds (naming it), is idempotent for a pair the target already carries, and is deliberately NOT routed through `update_transaction`/`create_transaction`'s rebuild — that would re-run the rules engine and could silently recategorize an Uncategorized row as a side effect of a metadata-only link. `mutates=("ledger",)`, no `connector=` tag (it operates on the ledger row, not one provider). The other deliberate removal path, `services.ledger.detach_external_ref` (`POST /api/transactions/{id}/refs/detach`, the drawer's "Unlink source"), is NOT a tool — it records a `different` decision in the match-engine's own verdict store so both strong-duplicate refusal sites skip re-colliding with that pair on a future fetch.

**`update_transactions` (2026-07-19 merge, `docs/adr/2026-07-19-merge-update-transaction-tools.md`)** — the SAME asymmetry `add_transactions` already fixed: `update_transaction` sat in `CORE_TOOL_NAMES`, `bulk_update_transactions` did not, so a 7-row "set memo to X" request cost 7 round trips (7 confirm cards) instead of one — the model had no reason to go hunting for a bulk variant it couldn't see. Merged `update_transaction` + `bulk_update_transactions` into ONE plural tool, mirroring `add_transactions`' shape exactly. **Shape:** one `updates` ARRAY parameter (`items: [{transaction_id, ...changes}, …]`, mirroring `add_transactions`' own `transactions` array byte-for-byte, INCLUDING the choice NOT to expose a list-or-scalar `anyOf` here — measured: an `anyOf[object, array-of-object]` over this rich a per-row shape roughly DOUBLES its schema bytes, since JSON schema for tool-calling can't `$ref` the branches, and that alone tipped `TOOL_SCHEMAS`' total over `tests/test_tool_schema_budget.py`'s cap; the plain array is both cheaper and the truer mirror of `add_transactions`, which never advertised its own single-row convenience in the schema either) — `[{transaction_id, ...changes}, …]` covers BOTH "the same change on N rows" (repeat the fields in every item) and "a different change on each" (the old shared-changes-only bulk shape couldn't express this at all); a bare single object, or bare top-level fields with no `updates` key at all (the old `update_transaction` call shape), are still accepted — CODE-level leniency only, same as `add_transactions`' own undocumented bare-fields path — and stay the trivial one-row path, routed through `_update_one` exactly like `add_transactions`' `_add_one`. `cleared`/`needs_review` (formerly bulk-only) are promoted onto the per-row patch too, so a single-row call can flip them without a second tool; `cleared` still routes through its OWN choke (`services.ledger.set_transaction_cleared`, the narrower Starting-Balance guard) rather than the generic patch rebuild. **Old names kept working via decorator `aliases=("update_transaction", "bulk_update_transactions")`** (mirroring `add_transactions`, not the retroactive `_LEGACY_TOOL_ALIASES` table — no stored data predates this canonical name). The pre-merge `bulk_update_transactions` shape (`transaction_ids` + ONE shared change-set at the top level) is still recognized — routed straight through the UNCHANGED `services.ledger.bulk_update_transactions` choke (not decomposed into per-row generic edits) so its additive-tags-union, kind-aware skip-with-reason (adjustment/category, transfer/payee) and auto-move `to_account_id` sugar keep working byte-for-byte for an old stored caller; it is not advertised on the new schema. **Confirm gate, extended to bulk (deliberate hardening):** `bulk_update_transactions` used to write immediately with no card at all — the merge closes that gap, so EVERY shape (single row, the new per-row array, and the legacy shared-changes shape) now previews first on a card-capable surface. A multi-row edit gets ONE card (`type="txn_bulk_update"`, 12-row sample, `count` over all N — mirrors `preview_bulk`'s add-side contract) built by looping the existing `ledger_preview.preview_update` per row (no new function added to `services/ledger_preview.py` — out of this lane's edit scope) plus a hand-computed `cleared`/`needs_review` diff entry (neither flows through `_DIFF_FIELDS`, since `cleared` has its own choke and `needs_review`, though it flows through the generic rebuild, was never enumerated there). A batch where any row fails to preview aborts wholesale (nothing staged) — the same atomicity contract `add_transactions`' Phase-1 validation gives creates.

**Write-then-verify — the ledger confirm gate is OFF (ADR `2026-07-20-write-then-verify-chip`, supersedes the POLICY half of `2026-07-19-ledger-confirm-gate-one-tool-stored-args`; the MECHANISM below is kept intact and re-armable).** `GATED_TOOL_NAMES` is now EMPTY: an ordinary ledger write COMMITS immediately and the reply carries ONE differential chip per TURN saying what landed. Owner: "do we really need to show these confirm cards at all though? ... i would rather see the chip of newly created/updated ones in the ai response and then tap on it to see the details" / "bulks, i can understand / the rest, bullshit" — the surviving requirement is legibility, not permission. **Collection** is a ContextVar seam (`core/write_receipt.py`, `core.audit_context`'s shape) fed from the ONE audit choke every create/update/delete already funnels through (`services/audit.py`) — NO ledger write path was modified; it is CLOSED by default, so a REST/import/migration/test write records nothing and "the chip shows what THIS turn wrote" holds by construction. **The differential** (`services/write_receipt.py`) surfaces only what is ANOMALOUS — `rule_override` (a rule DECIDED the stored category, read off the audit event's existing `rule_applied` provenance — the highest-value flag, since that silent resolution is what the confirm gate's own forensics blamed), `new_payee`, `uncategorized`, `large_amount` (>=5x the book's OWN median, SKIPPED entirely below 20 comparison rows — never a currency-denominated floor); a correct ordinary write raises none and renders a bare count. **There is NO Undo on the chip** (owner, 2026-07-20: "please stop having these undo! just show!") — the chip reports, it does not reverse; the writes stay recoverable via the turn checkpoint / the `txn_audit` table / soft-delete, which is not this component's job, and the `undoable` field is gone from the wire shape. The receipt is still stored ON the checkpoint index entry, so it is rebuilt on reload (`ckpt.turn_receipts` → `rehydrate_messages`, keyed on the same `anchor_history_len` the Restore anchor uses). SSE `write_receipt` (emitted next to `checkpoint_created`; `api/chat.py` passes events through verbatim, unchanged); UI `components/chat/WriteReceiptChip.tsx`, tapping a row deep-links the REAL drawer via `/accounts?txn=<id>`. **The chip is MULTI-TYPE (ADR `2026-07-20-generalize-write-receipt-beyond-transactions`)** — `record_write(op, entity_id, *, entity_type="transaction", meta=None, rule_applied=None)`: `op` is a CLOSED `create|update|delete` vocabulary (a domain verb — acquire/dispose/vest/merge/assign/pause — maps onto one of the three at its choke and rides in `meta["verb"]`, so the chip head never grows per-domain verbs), and `entity_type` MUST be a registered mention type (unregistered = dropped by the reader, pinned by `tests/test_write_receipt_multi_type.py`). The default + the DEPRECATED `rule_applied` alias exist so `services/audit.py` needed ZERO edits and the transaction path is byte-identical. Ten more chokes report, each recording ONLY the entity IT is the choke for (a vest cascades an income txn AND a lot; each reports itself through its own choke — recording the cascade twice would double-count): `lots.apply_lot_change` (lot/disposal), `equity.apply_equity_change` (grant/vest), `income.apply_income_change`, `agents.apply_agent_change`, `scheduling.apply_scheduled_task_change`, `alerts.apply_alert_change`, `planning.apply_budget_change` (envelope/category — reported INSIDE each `_op_*`, never in a wrapper, because `domain_introspect_ast` DERIVES each op's field set from the dispatcher source and a wrapper reading `change` would be attributed to all 21 ops; GROUP ops record NOTHING since they write no envelope row), `ai/tools/skills.apply_skill_change` (in `ai/`, which is why the seam must live in `core`), `match_review.merge_transactions_preserving_fields` (meta-only — the same `(type, op, id)` folds into the audit choke's existing record). Records DE-DUPLICATE on `(type, op, id)` merging meta, so an auto-assign + correction is one row, not two. **Every row is a real `MentionRow`** hydrated ONCE at turn end by `services/mentions/labels.py::receipt_rows(pairs)` — ONE store read per TYPE, never per row; same `_row()` helper + `ICONS` table as the search path, so a receipt chip and a picker chip are byte-identically shaped and `components/chat/lucius/Chip.tsx` renders both. `resolve_mentions()` is deliberately NOT used (it echoes the caller's label, caps at 12, can splice network context). A missing entity emits a `stale: true` row with an EMPTY label (absent = "no label available"; a fabricated name is a wrong claim). Head groups (`[{type, count, ops}]`, ≤2 + "+N more") make the head NAME the type — "1 envelope edited", never a bare "1 edited". DEFERRED (each needs a choke BUILT first, none permanently blocked): accounts (highest value), payees, rules, watchlist, commitments, targets, instruments; `options` also needs an `option` mention type; `positions` surfaces one id for three written types. PERMANENTLY OUT: singleton documents (profile/budgets/connector configs) — no entity, no id, and a `document` pseudo-type would render a chip resolving to nothing. **Confirmation SURVIVES only where the MODEL chose the SET of rows** — the global `apply_payee_rules` (`confirm=true`) and `delete_transactions_where`; both were always outside `GATED_TOOL_NAMES` (hardline-blocked unattended via `ai._confirm_gate.HARDLINE_UNATTENDED_TOOLS`), so emptying it does not weaken them. KNOWN GAP on the BOARD, not fixed here: `delete_transactions_where` has no INTERACTIVE confirmation at all. Acceptance: `docs/qa/acceptance/write-verify-chip.md`.

**Ledger confirm gate — the retained MECHANISM** (ADR `2026-07-19-ledger-confirm-gate-one-tool-stored-args`; OFF by policy since 2026-07-20, re-arm by adding a name back to `GATED_TOOL_NAMES`) — when armed, `add_transactions` and `update_transactions` (`GATED_TOOL_NAMES` in `ai/tools/_confirm_gate.py` — both the flag and the policy, so rollback per tool is deleting a string) PREVIEW instead of writing: they validate, build a pure preview via `services/ledger_preview` (`preview_create`/`preview_update`/`preview_bulk` → `proposed_change` types `txn_create`/`txn_update`/`txn_bulk`), stage the validated args under a single-use token in `db/pending_plan_store.py` (`pending_plans.json`, DATA_DIR, chmod 600, cap 200, checkpoint-EXCLUDED; the 15-min TTL applies to these legacy minted-token preview rows ONLY — an awaiting-approval row NEVER expires, ADR `2026-07-30-approvals-never-expire`), and return a card. The turn ends on the existing `emitted_proposed` terminator — no `assistant.py` change. The card's ✓ re-calls the SAME tool with `confirm_token`, which POPS the stored args and executes **those** — every other argument on the confirming call is DISCARDED, so a card showing $12.40 can never commit $1,240 no matter what the model reconstructs from history (the `McpPendingCallStore` stored-args pattern; `AlpacaPendingOrderStore` was a third instance until the Alpaca trading half was removed 2026-07-19). The staged plan ALSO records the outcome the card promised (resolved category, base amount, row count); the confirm re-resolves and REFUSES on mismatch, because redemption re-runs category resolution and `create_automation` (a `txn`-triggered categorization rule)/`set_payees_default_category` are ungated tools reachable in the SAME turn as the confirm — binding args alone would let a model (or an injection already in context) commit a category the user never saw. One tool per write, NOT a propose/apply pair; dispatch interception was deliberately deferred (it makes the confirm a primary write path outside the turn, and `_fix_dangling_tool_uses` only inspects `history[-1]`, so a spliced message orphans a `tool_use` unhealably → permanent session 400). A bulk add is ONE card for N rows (12-row sample, totals over all N; the resolver takes preloaded `rules`/`category_rows`/`rates` so a 500-row preview isn't thousands of store reads on the event loop). **The gate keys on a CARD-CAPABLE SURFACE — `core.cost_context.get_cost_surface() == "web"` — NOT on "is this interactive"** (security review: an inbound Telegram/Slack turn is deliberately NOT unattended, so an interactive test passes — but a connector renders the card through `format_change_summary` and applies it through `chat/confirm.apply_change`, so gating is safe only once both understand the change shape). Every other surface — scheduled, MCP, REST, imports — is unchanged, and the predicate FAILS OPEN, because an ungated write is the status quo while a staged write nobody can confirm is a broken workflow. Skill activation is deliberately NOT an exception: it cannot preapprove or bypass the gate. Known limit (deliberate): a bulk `already_recorded` abort surfaces after the ✓. Acceptance: `docs/qa/acceptance/ledger-confirm-gate.md`. **Two invariants the preview shares with the write, both merge-critical (2026-07-19, integrating the account-ref-resolution lane):** (1) account NAME → id resolution (`_resolve_account_refs`) runs INSIDE `resolve_transaction_row`, so the preview resolves exactly what the write resolves and the card shows the account NAME — AND still runs in `create_transaction` before `matching.check`, whose L0 dedup key is built from account ids (a name resolved only in the resolver would hash to a different row and slip the guard); the double call is idempotent and free, since `_resolve_account_refs` returns `data` untouched once every ref is an id. Git merges the two hunks cleanly while leaving the resolver unable to resolve a name at all, so this is pinned by `test_preview_resolves_an_account_NAME_exactly_as_the_write_does`. (2) Preloaded FX `rates` come from `core.fx._load_rates` — the loader seam `to_base(rates=None)` resolves through — NOT `services.fx_cache.load_fx_cache`, which reads the cache file directly and bypasses that seam; the two are only incidentally the same table, and pricing a card off the other one previewed (and committed) a 250,000 VND leg as 250,000 base instead of 30.00. `preview_bulk` and `bulk_create_transactions` both preload from `_load_rates`, pinned by `test_preview_bulk_prices_base_off_the_SAME_rate_source_as_the_write`. **Connectors now redeem the same staged token (2026-07-19, ADR `2026-07-19-confirm-gate-surface-matrix`):** `connectors/chat/confirm.py`'s `apply_change` gained a `txn_create`/`txn_bulk`→`add_transactions`, `txn_update`→`update_transaction` branch that redeems the card's `confirm_token` via `ai.tools.execute_tool` (never re-deriving args from the connector's own `change` dict), and `connectors/processor.py`'s `format_change_summary` gained a FLAT-shape-aware formatter for the three ledger types (`services.ledger_preview` returns them with no `display` wrapper, unlike every other change type this function renders) — closing the "connectors would render a blind card and misapply through the positions choke" gap the paragraph above documents. **`_CARD_CAPABLE_SURFACE` is FLIPPED (2026-07-19, closing the item above):** `ai.tools._confirm_gate.should_gate` now calls `ai._confirm_gate.can_render_card(get_cost_surface())` instead of the old hardcoded `== "web"`, so a connector turn now DOES see (and can confirm) a ledger `proposed_change`, exactly like web chat. **The headless design's persisted home + composed guard are also BUILT:** `models.Agent.unattended_write_envelope` (`models/agent.py`) is the per-agent PRE-AUTHORIZED write boundary (JSON-shaped — lists, not frozensets); `services.agents.resolve_unattended_envelope(agent)` reads it, folding in a narrow, explicit, `builtin`-gated grandfather default for `email-transaction-logger` (the one legacy-critical agent an install may have seeded before this field existed — every OTHER agent with no declared envelope fails closed, by design, once wired: "no envelope = unconstrained for everyone" was rejected as the migration path since it would undo the entire point of failing closed for every agent, not just the one it was meant to protect); `ai.tools._confirm_gate.enforce_unattended_write`/`report_unattended_write` compose the hardline block, the envelope evaluation, and the best-effort surfacing into the ONE call a ledger write path should make. **WIRED (2026-07-19c, closing the ADR's last Follow-up):** every real write in `ai/tools/ledger.py` now calls it — `_add_one`/`_update_one` (single-row create/update, guard before the write, `report_unattended_write` after, both guarded on `is_unattended()`), the TRUE multi-row batch paths (`add_transactions`' statement-import `to_create` write and `update_transactions`' N>1 `updates` loop, evaluated PER ROW so a mixed in/out-of-envelope batch books the former and reports the latter rather than an all-or-nothing abort), and `delete_transactions_where` (the hardline check, unconditional refusal). An unattended caller — `email-transaction-logger` included — is now actually gated: inside its envelope it writes and notifies, outside it (or with no envelope declared) it is refused with a Signals row, never a raised exception; an interactive/connector/skill turn is untouched (the guard self-guards on `is_unattended()`, no second predicate). Deliberately left unwired: the alias-only `_update_legacy_bulk` path and `apply_payee_rules` (owned by `ai/tools/payees.py`). Verified end-to-end in `tests/test_ledger_unattended_write_wiring.py`. **STATUS CORRECTION: this whole envelope mechanism is INERT since 2026-08-10** (`ai/tools/_confirm_gate.py::enforce_unattended_write`'s own docstring says so plainly) — `models.Agent` no longer exists (the Agent/Rule/Scheduling tool groups were unified into `automations` on 2026-08-02, see "Automations" below), so `models.Agent.unattended_write_envelope`/`services.agents.resolve_unattended_envelope` are gone with it. For a scheduled Automation caller the live hardline check is now `automation_gate_verdict`'s `auto`-mode branch (`is_hardline_blocked`, same file); a non-Automation unattended caller (e.g. `ai/capture.py`'s iOS tap-to-log) currently has NO hardline check at this call site at all. Treat every claim above this line as history, not current wiring.

**Documents (ADR `2026-09-26-vault-is-a-view-over-existing-stores`; internally the Vault):** `list_documents` (metadata only — kept files, saved artifacts, statements, receipts, asset files; `kind`/`year`/`tag`/`query` filters; each item carries the user's `note` and `tags`, 20 per page, max 50), `read_documents` (≤5 ids; a 24k-character budget per call split across them, `offset` pages one long document; images/scanned PDFs go through the same configured reader as `read_attachments`; a Private file is REFUSED before any content loads — `services.vault.read_source`), `save_to_documents` (`mutates=("vault",)` — keep an artifact or a chat attachment when the user asks; can mark a file Private, can never switch Private off), `remove_from_documents` (`mutates=("vault",)` — the opposite, when the user asks: un-files an artifact or a chat file, which stays where it came from and can be saved again; REFUSES anything whose only home is Documents — statements, receipts, asset files, files added straight to Documents, an artifact whose conversation is gone — because removing those deletes them, `services.vault_changes.unfile_item`). No tool deletes from Documents — `delete_upload` refuses a file kept in Documents, and `get_uploads` flags `in_documents`/`private` (a Private row's content-derived `summary` is dropped). A file marked Private is also refused by `read_attachments`, the import/equity-PDF parsers, `diff_statement` and receipt promotion (`services.attachments.get_attachment_for_model` / `private_refusal`).
