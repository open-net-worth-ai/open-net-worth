# Architecture / Agent Decision Records (ADRs)

An ADR records a decision **already made** — the choice, the forces behind it, and the
alternatives rejected — in one short, numbered, append-only file. This repo is largely
**agent-built**, so the *why* behind a build choice tends to evaporate into the diff. ADRs make
that reasoning recoverable: each one captures not just the architectural call but **which agent
made it, on which lane/branch, and why** (see the **Agent provenance** block in every ADR).

## When an ADR is REQUIRED

Write one when a decision is any of:

- **Cross-cutting** — touches multiple layers/modules or every caller of something.
- **Hard to reverse** — a data-model shape, a write choke point, an external contract.
- **Convention-deviating** — it bends or breaks a stated convention/invariant in `CLAUDE.md`
  (the dependency rule, a write choke point, an "always recompute" invariant, etc.). If you have
  to justify *why the rule didn't apply here*, that justification belongs in an ADR.
- **A non-obvious build choice an agent made mid-task** — where the chosen approach isn't the
  one a reader would assume from the code alone.

Routine, easily-reversible choices (a local refactor, a rename, an obvious bug fix) do **not**
need an ADR. When in doubt: would a future agent waste time relitigating this, or be surprised by
it? If yes, write one.

## The ADR is the home of the reasoning — do NOT re-narrate it in `CLAUDE.md`

Writing an ADR **replaces** explaining the decision elsewhere; it does not duplicate it.
`CLAUDE.md` is loaded into *every* turn, so prose pasted there is paid for on every request,
forever — including on turns that never touch the area.

Once the ADR exists:

- **`CLAUDE.md`** gets at most a **one-line statement of the resulting rule**, plus the ADR id.
  Not the incident, not the alternatives, not the lane log. If the rule only matters once you are
  already reading a specific file, it does not belong in `CLAUDE.md` at all.
- **The area's doc** (`docs/DATA_MODEL.md`, `docs/PLANNING_MODEL.md`, `docs/ai/…`) gets the
  operational detail a reader needs while working there.
- **The ADR** keeps the full why: forces, alternatives rejected, the incident, Agent provenance.

This is the rule that was missing while `CLAUDE.md` grew to 201 KB (~50 k tokens/turn) by
inlining 47 ADRs that already existed as files. If you find yourself pasting an ADR's narrative
into `CLAUDE.md`, link it instead.

## ADR vs RFC vs PRD

| Type | When | Where | Shape |
|---|---|---|---|
| **PRD** | Product spec / acceptance criteria — *what & why for the user* | `docs/prd/` | Problem, scope, acceptance criteria |
| **RFC** | Forward-looking **design proposal**, pre-build — *how we intend to build it* | `.claude/rfcs/` (earlier ones in `docs/rfc/`) | Heavy: approach, layers, alternatives, trade-offs |
| **ADR** | A decision **already made** — *the decision of record* | `docs/adr/` | Short, numbered, append-only |

An RFC proposes; an ADR records. An RFC can be revised before the build; an ADR is **never edited
away**. To change a recorded decision, add a **new** ADR and flip the old one's status to
`Superseded` with a link to the replacement (see "Authoring").

## Numbering & filenames

- **New ADRs (2026-06-28 onwards):** date-prefixed filenames — `YYYY-MM-DD-kebab-title.md` (e.g. `2026-06-28-adr-filenames-are-date-prefixed.md`). Sequential numbers caused collisions under parallel/multi-agent authoring; date-prefix matches the convention already used by `docs/superpowers/specs/` and `.claude/rfcs/`. See `2026-06-28-adr-filenames-are-date-prefixed.md`.
- **Existing ADRs (`0001`–`0029`)** keep their four-digit numbers; do not renumber them.
- `0000-template.md` is the template, not an ADR — never counted, never given a status.

## Authoring

- Run `/adr` (the skill at `.claude/skills/adr/SKILL.md`) — it finds the next number, copies the
  template, fills it in, and updates the index below.
- Or by hand: copy `0000-template.md` to `docs/adr/NNNN-kebab-title.md`, fill the front-matter and
  every section (including **Agent provenance**), then add a row to the Index.
- **To supersede:** add the new ADR, set the old ADR's `status:` to `Superseded`, and link the new
  one from the old (and vice-versa). Do not delete or rewrite the superseded record.
